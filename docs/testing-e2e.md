# E2E tests (Playwright, Chromium)

From `src/ui/PartyKing.UI`: `npm run e2e`, about 8 min, 70 tests. First time only: `npx playwright install chromium`. Typecheck the suite with `npx tsc -p e2e/tsconfig.json`; `vite.config.ts` keeps `e2e` and `playwright.config.*` out of vitest.

## Setup

- `playwright.config.ts` starts both servers itself and never reuses running ones, so stop your dev API and Vite first (ports 4200 and 2137).
- `e2e/start-api.mjs` runs the API in the `e2e` environment (`ASPNETCORE_ENVIRONMENT=e2e`) on a throw-away database. The web root and the *content root* are in the git-ignored `e2e/.work` (wiped on each start), so your `appsettings.Local.json` (which would override env vars) is not read. The committed `appsettings.json` and `appsettings.e2e.json` are copied there (`appsettings.Development.json` is not loaded in this environment). `PartyKing.API/appsettings.e2e.json` holds only what the e2e run changes: today it raises the log level of the auth handlers to Warning, because every anonymous request logged "was not authenticated" and CI prints the whole log (about 5,800 lines of it). The development helpers (CORS for Vite, Swagger, `DevPersonaMiddleware`, the two switches below) are tied to `IsDevelopmentOrE2e()` (`PartyKing.API/Development`), so the e2e environment has them and Production never does. Admin: `e2e-admin` / `e2e-admin-password`. `RateLimiting__Disabled=true` — honoured in Development and e2e only (`Program.cs` skips `UseRateLimiter`), because the suite logs in and unlocks sessions far more often than the 10/min limits allow. `Resistance__Seed=931902` — also Development and e2e only (`SeededRandomProvider`): every Resistance action that needs randomness (the deal of roles and first leader, the plot deck shuffle, the card taken by Take Responsibility) gets a `Random` from this seed, so the same number of players joining in the same order always get the same deal (a different player count deals differently). Then `npm start` runs Vite.
- The e2e API runs without `LlmSettings:ApiKey` on purpose, so the specs also guard that Ringo works without one.
- `global-setup.ts` logs the admin in once (`POST /account/login`) and saves the cookies to `e2e/.auth` (git-ignored). A spec that needs the admin as well as anonymous or user API contexts must not use `test.use({ storageState })`: Playwright also applies it to every `request.newContext()`, so an "anonymous" context would carry the admin cookie (see `admin-users.spec.ts`).
- One worker; tests share one API and database.
- The base URL must be `http://127.0.0.1:2137`, not `localhost` (the login cookies don't reach the API).
- Selectors are roles and labels with the English texts.

## Fixtures (`e2e/fixtures/test.ts`)

- `createSession` creates sessions through the admin API and deletes them after the test; `unlockSession` types the password.
- `openAdmin` / `openGuest` give each player their own browser context (own cookies, so own player identity; no `?persona=` needed).
- `e2e/fixtures/resistance.ts`: `startResistanceGame(session, openers, { players })` — the admin creates, opens and starts a game with 5 to 10 guests; the helpers for playing it are under "Resistance helpers".

## Specs

- `accounts.spec.ts`: a visitor signs up through the dialog, stays signed in after a reload, logs out and back in; a taken username (any case) and a wrong password are refused; changing the password (old one stops working, a wrong current one changes nothing); "log out everywhere" ends another browser's login; deleting the account; a user is turned away from `/admin`. `e2e/fixtures/accounts.ts` has `registerUser` (API) and the dialog helpers.
- `admin-users.spec.ts`: an admin pages (22 users, two pages) and searches the users; resets a password (the user's old cookie dies, only the new password logs in); a password under 8 characters is not accepted; a user gets 403 and a visitor 401 from `/admin/users`; an admin's own password cannot be reset.
- Home smoke; admin login and session creation; wrong-password and right-password unlock; the language switch.
- Photo upload (and a refused fake image).
- `suggestions.spec.ts`: Never have I ever statements and Ringo ace rules come from the built-in lists with the "AI is unavailable" notice. The Ringo one flips cards as the admin until an ace shows, since the deck is random.
- `session-settings.spec.ts`: rename shows on Home; a password change sends guests back to the password form but keeps the admin in.
- `join-qr.spec.ts`: the token is read from the `join-token` response, because the dialog shows only a QR image; a guest opening `?join=<token>` gets in; a bad token shows the password form.
- `saved-playlists.spec.ts`: a guest without an account has no save-as-playlist button and the API answers 401; a guest who signed up queues three YouTube links (one twice), opens the dialog (name starts as the session name, only "Up next" can be chosen, with its count), saves and is told two songs were saved; a session without songs has Save disabled. The songs are queued through the API with the guest's cookies (the oEmbed lookup falls back to the URL when YouTube is unreachable); the playlists cannot be read back yet, so nothing checks the stored rows (the repository tests do).
- `guest-access.spec.ts`: a guest has no settings or QR button, and `/s/:id/games` redirects to the session.
- `photos-admin.spec.ts`: an admin sees the empty slideshow and a disabled "Download as ZIP"; after an upload, the photo in the slideshow, the count in Session settings and a real zip download. The slideshow `img` has no alt text, so it is found by `.photos-slideshow img`.
- `resistance-lobby.spec.ts`: an admin creates and opens the game, five guests join and the admin starts it; each player gets a role card, the admin none, a latecomer is told it started. A taken name is refused, and a kicked player is told.
- `ringo-lobby.spec.ts`: two guests join, only the player on turn can flip, the flip and "Continue" work. Ringo's cards are scattered at random and overlap, so the spec sends the click to the element (`dispatchEvent('click')`) and not through the pointer.
- `resistance-round.spec.ts`: a full game of three successful missions to "Game over", and a rejected team that passes the lead on, the team picker (leader only, exact size) and a tied vote at six players.
- `resistance-spies-win.spec.ts`: three failed missions (banner, revealed roles on the admin's board), five rejected teams in a row, and the Fail card being disabled for the Resistance.
- `resistance-hidden-info.spec.ts`: only spies are told who the spies are (screen and API), the admin and a watching guest get no role, an admin who plays gets none on `?tv=1`, votes stay secret until the last one and can be changed until then.
- `resistance-lifecycle.spec.ts`: restart a finished game with the same players; "End game" asks first, then sends everybody away.
- `resistance-plot-cards.spec.ts`: the add-on turned on with `startResistanceGame(..., {plotCards: true})`. Five players: the leader deals the drawn Open Up, its holder plays it, the target confirms the identity card; on the next mission a Strong Leader takes the lead in the Leader window after a rejected team (not given to the next seat, who leads after the rejection anyway). Seven players: an Opinion Maker votes first and a No Confidence card rejects the approved team in the Confidence window (counts as a rejected team). Nine players: Take Responsibility takes the visible Opinion Maker from its holder, who then votes first (the Keeping a Close Eye left in a hand opens the Confidence window). Six players: an Overheard Conversation shows the identity card of a neighbour (the picker lists exactly the two seat neighbours) to its holder only.
- `resistance-plot-cards-windows.spec.ts`: the cards that need windows. Ten players, first mission: the leader plays Establish Confidence, an approved team opens the Confidence window (only the No Confidence holder is offered a card), and after the mission cards the Keeping a Close Eye holder looks at one in the Peek window (only they see it; the log shows who looked at whom). Six players, second mission (after an Overheard Conversation played at once, so no card is in a hand): the In the Spotlight holder forces a team member to play their mission card openly, which everybody sees in the banner.
- `resistance-inquisitor.spec.ts`: five players with the Inquisitor module (`startResistanceGame(..., {inquisitor: true})`). The token is public from the start; mission 1 has no Inquisition. After the failed mission 2 the holder's picker lists everybody else, the examined player's real loyalty is shown to the holder only (every other player and the admin get `yourInquisition: null` from the API), the token is already the examined player's, and "Next" waits for the holder's confirmation. After mission 3 the new holder cannot pick either earlier holder. Without the module there is no token and no Inquisition. Helpers: `playMissionToInquisition`, `examineOptions`, `examinePlayer`, `confirmInquisition`.
- `resistance-reverser.spec.ts`: five players with the Reverser module (`startResistanceGame(..., {reverser: true})`). Exactly two players have `yourCharacter: 'Reverser'`, one per side, and only they get the role card note and an enabled Reverse card (the others on the team see it disabled, a spy Reverser's Fail is disabled). The resistance Reverser plays Reverse and a non-Reverser plays Success on the first mission: it fails, and the result has `failCount` 0 and `reverseCount` 1 (the phase line says so too).
- `resistance-defector.spec.ts`: five players with the Defector module (`startResistanceGame(..., {defector: true})`). Exactly two players have `yourCharacter: 'Defector'`, one per side, and only they get the role card note; the spy Defector's `fellowSpies` is `[]` and the other spy's lists them. After two successful missions the third one starts with a public flipped switch card (`defectorFlips`, drawn on the admin's mission board as an image named "Mission 3: No Change" or "Mission 3: Change Allegiance"; the banner has its own "Latest switch card (mission 3): ..." image); the spec reads it and checks the Defectors' `yourRole` and the spies' `fellowSpies` for both outcomes of the flip (the seed decides which one runs).
- `resistance-assassin.spec.ts`: five players with the Assassin module (`startResistanceGame(..., {assassin: true})`). One Commander (resistance, `fellowSpies` lists both spies) and one Assassin (spy), and only they get their role card note; after three successful missions every view is in `Assassination` with `winner` and `revealedRoles` null, only the Assassin has the "Player to name" picker and everybody's phase line says the Assassin is choosing. Naming the Commander gives the spies the win (`assassinationTargetPlayerId`, the reason in the banner), naming anybody else the resistance, and the host can restart from the game over screen and from the Assassination (an absent Assassin). `playMission` knows the `Assassination` phase. Two more tests cover the optional characters (`startResistanceGame(..., {assassinCharacters: [...]})`): seven players with Body Guard, Deep Cover and Blind Spy (the Commander's `fellowSpies` leaves out Deep Cover, the Blind Spy's is empty and the Assassin's lists only Deep Cover, only the Body Guard has `yourCommanderCandidates`), and five players with Body Guard and False Commander (two candidates, one of them a spy).
- `resistance-blind-spies.spec.ts`: five players with the Blind Spies variant (`startResistanceGame(..., {blindSpies: true})`). A spy's `fellowSpies` is an empty list and the card shows the "Blind Spies" note instead of the list, a resistance member still gets `null` and no note, and nobody sees a "Fellow spies" list.
- `resistance-two-fails.spec.ts`: seven players, fourth mission (two Fail cards needed). One Fail card among the four team members does not fail it (the fifth mission, which needs one, then does), two Fail cards do. The outcomes of the first three missions are chosen so that nobody has won by then.
- `resistance-seat-takeover.spec.ts`: the host releases the seat of a player whose context was closed (needs the presence grace of 10 s, so the test waits up to 30 s for the button to enable); a new context claims it from the "Back in the game" picker; an unreleased seat is not offered.
- Not covered: anything needing Spotify or YouTube (host login, the player, search), reordering the seats, and the Polish texts of a game.

## Resistance helpers

Roles and the first leader are seeded in e2e but depend on the player count and the order of joining, so the helpers still find out who is who instead of hard-coding it:
- `viewOf(page, session)` / `viewOfPlayer(setup, name)` read `GET /sessions/:id/games/resistance` with that player's own cookies (they are shared across ports on 127.0.0.1). It is exactly the player's view of the game, so it also proves what a player must not know (`votes`, `fellowSpies`, `yourRole` of someone else). Use it to find who has to act (`waitForLeader`, `spyNames`, `waitForPhase`); the acting itself goes through the UI.
- `waitForPhase` polls, because a click returns before the server has answered. Call it (or `waitForLeader`) between steps and not `isVisible()`.
- The helpers keep a ten-player game under the 60 s test timeout (`playwright.config.ts`; a CI runner is slower than a laptop, and 30 s was too little): `startResistanceGame` opens all guest pages at once (the joining stays one by one, as the seats follow the order of joining), and `voteAll`, `playMissionCards` and `passWindow` click on all pages at once (`voteAll` lets an Opinion Maker go first, alone). Keep new helpers parallel where the order does not matter.
- `submitTeam`, `vote`, `voteAll`, `continueMission`, `rejectTeams`, `playMissionCards(setup, team, failers)` and `playMission(setup, 'success' | 'fail', fails?)` play a round. A failed mission puts as many spies on the team as it needs Fail cards (or `fails`).
- The team picker's checkbox is covered by a tick, so the tests tap the player's name inside the "Pick the team" group. Once the team is full the other checkboxes are disabled.
- The Approve/Reject/Success/Fail cards are `role="button"` SVGs inside the "Voting" and "Mission" regions.
- The mission panel disappears with the last card, so the tests do not wait for "Card played".
- `?tv=1` only means something to the host and admins; a plain player with it gets the player view.
- The game-over banner text comes from `resistancePhase.ts`; an expansion that changes it also changes the specs that assert it.

## CI

The `e2e` job of `ci.yml`: setup-dotnet and setup-node, a cache of `~/.cache/ms-playwright` keyed on the Playwright version, `npx playwright install chromium`, `npm run e2e`. There is no `--with-deps`: the runner has every library Chromium needs, and the flag only added CJK and X11 fonts through apt, which took over 5 minutes; add it back if a runner image ever lacks a library. With `CI` set Playwright retries a failure once and writes an HTML report, uploaded with the traces as an artifact on failure. `deploy.yml` reuses `ci.yml`, so a failing e2e job also blocks a deploy.

### Plot cards

The deck is always the same 15 cards; what is drawn depends on the seeded `Random` (`Resistance__Seed=931902`, see Setup) and on the number of players, which is why a spec states the player count and checks what the leader drew (`waitForDealing` returns `drawn`) before it relies on it. With the current seed (cards per round: 1 for 5-6 players, 2 for 7-8, 3 for 9-10):
- 5 players: Open Up on mission 1, Strong Leader on mission 2.
- 6 players: Overheard Conversation on mission 1, In the Spotlight on mission 2.
- 7 players: Opinion Maker and No Confidence on mission 1.
- 9 players: Opinion Maker, Keeping a Close Eye and Take Responsibility on mission 1.
- 10 players: Establish Confidence (kept by the leader), Keeping a Close Eye and No Confidence on mission 1.

The seed was picked by searching for one that gives these draws, because the specs need particular cards (the deck is shuffled with `Shuffled`, so any change to the shuffle or to the order the deal draws random numbers in changes them).

If the deal code changes, the `drawn` assertion fails first; read the new order from the leader's view (`yourPlotCards`, `toDeal`) and adjust the specs. Helpers: `startResistanceGame(..., {plotCards: true})` / `enableModule(admin, 'Plot cards')` (the checkbox only ticks after the server answers), `waitForDealing`, `dealPlotCards(leader, {OpenUp: 'Bartek'})`. `playMission`, `submitTeam` and `playMissionCards` do not know the windows (nor the Inquisition of the Inquisitor module: use `playMissionToInquisition` after mission 1): once a playable card is in a hand (an Opinion Maker does not count), a rejected team opens the Leader window, an approved one the Confidence window, the last mission card the Peek window, and each mission starts with a Leader window before the draw. Every player has to pass (or play) before the game goes on. `passWindow(setup)` makes everybody pass the open window (wait for the phase first), `playMissionThroughWindows` plays a whole mission through the Confidence and Peek windows, and `pickTeam` is the team choice they share. `voteAll` lets an Opinion Maker vote first. Cards are played with `playImmediateCard`, `confirmIdentityCard` (returns whose card was shown and its role) and `takeResponsibility`; `dealPlotCards` takes an array for a card drawn twice.
