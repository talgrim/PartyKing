## Model and endpoints

- `ResistanceGame` (key `SessionId`; `CreatedAt`, `IsOpen`, `StartedAt`, `LeaderPlayerId`, `Phase`, `MissionNumber`, `RejectedTeams`, `Winner`, `Rules`, and for the Inquisitor `InquisitorPlayerId` / `InquisitionExaminerPlayerId`, and for the Assassin `AssassinationTargetPlayerId`) owns `ResistancePlayer` rows (`Role`, `Character`, `IsOnTeam`, `Vote`, `MissionCard`, `PassedLeaderWindow`, `IsReclaimable`, `WasInquisitor`), `ResistanceMissionResults` and `ResistancePlotCard` rows. `MinPlayers` 5, `MaxPlayers` 10 (a full lobby answers 409 `Resistance.Full`).
- The static helpers behind the game actions are split by job: `ResistanceFlow` (phase transitions, the vote and mission results, the public phase queries), `ResistanceDealer` (dealing roles, characters and the plot deck at the start, `Reset` at a restart) and `ResistancePlotCardQueries` (who may play or see which plot card). `ResistanceKnowledge` stays the one place for who knows whom.
- `ResistancePhase`: `SelectingTeam`, `Voting`, `PlayingMission`, `MissionResult`, `GameOver`, the unused `VoteResult` kept for stable numbers (a migration moved games parked in it to `SelectingTeam` with the same leader), and the appended plot-card phases `DealingCards`, `ResolvingCards`, `LeaderWindow`, `ConfidenceWindow`, `PeekWindow`, the Inquisitor phase `Inquisition` and the Assassin phase `Assassination`. The lobby is `StartedAt == null`. Phases are stored as ints, so only append.
- Controllers share the route `games/resistance` behind `ResistanceControllerBase`: `ResistanceController` (lobby and lifecycle, plus `rules/blind-spies` and `rules/reverser`; it also calls the round service for start and restart), `ResistanceRoundController` (team, vote, mission, continue, window pass), `ResistancePlotCardsController` (everything under `cards/` plus `rules/plot-cards`), `ResistanceInquisitorController` (`rules/inquisitor`, `inquisitor/examine`, `inquisitor/confirm`), `ResistanceAssassinController` (`rules/assassin`, `assassin/target`) and `ResistanceSeatsController`.
- Lobby endpoints:
  - `GET` — host, admin and joined players; guests who unlocked the session observe once the game is open (404 before).
  - `GET lobby` → `{createdAt, isOpen, isStarted, joined}`. `IResistanceGamesRepository.GetLobbyAsync(sessionId, playerId, playerStamp)` projects those fields with one `AsNoTracking` query into a `ResistanceLobbyState` (null without a game) and does not use the shared read, because every tab asks for the lobby on its pushes (it shows as `operation="GetLobbyAsync"` in the repository histogram). `joined` follows `GameLobby.IsPlayer`: the host and admins are not players by role.
  - `POST` create (host or admin, 409 when one exists), `POST open` (admin only, idempotent), `POST join` (`session-join` rate limit), `DELETE players/{id}`, `PUT players/order`, `DELETE` (end).
- Pushes: `ResistanceChanged` (every action) and `ResistanceOpened`; the UI revalidates `resistanceKey` / `resistanceLobbyKey`.

## Services

`Application/Games/Services/Resistance` has five scoped services that match the controllers:

- `IResistanceLobbyService`: get, lobby, create, open, join, rules, plot-cards, Inquisitor and Blind Spies switches, kick, reorder, end.
- `IResistanceRoundService`: start, restart, team, vote, mission card, continue.
- `IResistancePlotCardService`: deal, play, confirm, take responsibility, take lead, peek, no confidence, pass window.
- `IResistanceInquisitorService`: examine, confirm.
- `IResistanceAssassinService`: name the Commander (`AssassinateAsync`); the module switch is `IResistanceLobbyService.SetAssassinAsync`.
- `ResistanceActionGate` (composition, not a base class, so it can be tested alone) runs a player or manager action: access check (`RunAsPlayerAsync`: caller must be allowed and a game must exist; `RunAsManagerAsync`: host or admin), the action on the game through `UpdateAsync`, the failure-to-error mapping, and the caller's view.
- `ResistanceErrors` holds the shared errors and `From(outcome)`, one error per `ResistanceFailure`, pinned by the golden table in `ResistanceFailureErrorsTests`. Codes and messages are matched by the UI and tests: keep them stable.

## Rules snapshot

- Role counts, team sizes and required fails per player count are `ResistanceRules` (defaults in the Domain), overridable at runtime through `ResistanceSettings:PlayerCounts` (`IOptionsMonitor`). The validation rule is `ResistanceCountRules.Validate(playerCount)` in the Domain (returns `ResistanceRulesFailure`s); `ResistanceConfigurationValidator` only words the failures for the configuration path; `IResistanceRulesProvider` keeps the last valid rules.
- The setters of `ResistanceRules` stay public because the JSON column is read with System.Text.Json; every new property must also be copied in `ResistanceRules.Clone`.
- A game snapshots the rules in `ResistanceGame.Rules` (JSON column) at creation. `POST rules/refresh` (host or admin, 409 `RulesLocked` once open) re-reads them; the UI's "Refresh rules" button does that before the lobby is opened. `PUT rules/plot-cards` (see below) switches the add-on.

## Round flow

### Start

- `POST start` (host or admin through `AuthorizeManagerAsync`). `ResistanceGame.Start` needs an open game with at least 5 players (409 `NotOpen` / `NotEnoughPlayers` / `AlreadyStarted`), deals the roles with `ResistanceDealer.Deal` (spies are a third of the players, rounded up: 2, 2, 3, 3, 3, 4) and picks a random first leader, all in one save. The `Random` comes from `IRandomProvider` (`Create()` per action; `Random.Shared` by default). In Development and the e2e environment, `Resistance:Seed` replaces it with `SeededRandomProvider`, which hands out a new `Random(seed)` each time (used by the e2e suite; ignored in other environments).
- A started game locks its players: `LobbyGame` asks `IsLocked` (`IsStarted`) in join, kick and reorder, and the status is `LobbyStatus.Started` (409 `Resistance.Started`). `ResistanceLobbyDto.isStarted` hides the invite and makes `GameJoin` say the game already started.

### Roles are secret

- `ResistanceGameViewBuilder.Build(game, caller)` (`Application/Mappings`) gives `yourRole` only to a player of a started game and `fellowSpies` (player ids) only to a spy or the Commander, and what is in that list is decided by `ResistanceKnowledge.KnowsSpy` (see Blind Spies). Observers, including a host or admin who is not playing, get neither; `leaderPlayerId` is public. Pushes stay payload-free, so each client fetches its own view.
- UI: `ResistanceRoleCard` shows a face-down `CardBackIcon` that a tap turns into `SpyCardIcon` / `OperativeCardIcon` (local state, hidden again after a reload); a spy sees the other spies (`SpyMarkerIcon`) only while it is face up (with Blind Spies, a note that they know no one instead). `ResistancePlayers` puts `LeaderTokenIcon` next to the leader. Icons live in `resistance/ResistanceIcons.tsx`; without a `className` they size themselves from the viewBox with viewport-based `clamp()` classes (`DEFAULT_SIZE`), and the vote icons accept `onClick` / `pressed` / `disabled`.

### Team selection

- `MissionNumber` and `ResistancePlayer.IsOnTeam` hold the leader's team; `Rules.TeamSize(playerCount, mission)` reads the snapshot (the UI reads the same numbers from `rules` in the DTO).
- `PUT team` (`{playerIds}`) is leader-only through `AccessAsync` plus `callerPlayerId == LeaderPlayerId` in `ResistanceGame.SelectTeam`: 403 `NotLeader` (also for the host and admins, who get no override); 409 `NotStarted` / `TeamSubmitted`, or `NotSelectingTeam` in a leader window where no team exists yet; 400 `WrongTeamSize` / `UnknownPlayer`. It needs exactly the required number of distinct players and saves them in one go, which locks the team (`IsTeamSubmitted` = anyone `IsOnTeam`).
- There are no drafts on the server: `ResistanceTeamPicker` (in `ResistancePlayerView`, only for the leader of a started game without a team, never in the TV tab) keeps the picks local until "Zgłoś drużynę do głosowania"; it is keyed on mission and rejection count so its picks reset.
- The DTO has `missionNumber`, `requiredTeamSize` and the public `teamPlayerIds`; the boards mark the team ("W drużynie", ring) and the phase line names it.

### Voting

- Submitting the team sets `Voting` and clears old votes. `PUT vote` (`{approve}`) is for joined players only (403 `NotPlayer`, also for a host or admin who did not join; 409 `NotVoting` / `GameOver` / `NotStarted`). A vote can be repeated and is replaced until the last player has voted.
- `ResistanceGame.Vote` tallies in the same save as the last vote (`ResistanceFlow.ResolveVotes`): a strict majority of all players approves, a tie rejects. An approval resets `RejectedTeams`; a rejection increments it and the fifth ends the game (`GameOver`, `Winner = Spy`). An approved team goes to `PlayingMission`.
- A rejection needs no "Dalej": the lead passes to the next player by `Order` at once, the team (`IsOnTeam`) clears and the phase returns to `SelectingTeam` with the same mission. The votes are kept, so everybody sees who voted how until the new leader submits a team (`SelectTeamAsync` clears them).
- `ToDto` hides the votes: until all voted only `votedPlayerIds` (who, not how) and the caller's own `yourVote` are sent; `votes` / `voteApproved` appear once everybody has voted and the phase is not `Voting` (so also while the next leader picks after a rejection); `revealedRoles` only in `GameOver`.
- UI:
  - `ResistanceVotePanel`: the clickable `VoteApproveCardIcon` / `VoteRejectCardIcon` cards, themselves `role="button"` with `aria-pressed` and keyboard activation (no wrapping button); never in the TV tab or for observers, and `yourVote` is blanked for `?tv=1`.
  - `ResistancePlayerMarks` (voted tick, Za/Przeciw, revealed role) on `ResistanceCompactBoard` and the TV seats (`ResistancePlayers` `marks`).
  - `ResistanceVoteCards` on the TV layout, from the moment all voted until the next team is submitted after a rejection or the last mission card is played: one card per voter signed with their name, beside the team cards, which move to the left.
  - The rejection tracker on `ResistanceMissionBoard`.

### Missions

- `PUT mission` (`{card}`: `Success`, `Fail` or `Reverse`) is for team members only: 403 `NotPlayer` / `NotOnTeam`, 403 `MustSucceed` for a Resistance member playing Fail, 403 `NotReverser` / `ReverserCannotFail` (see Reverser), 409 `AlreadyPlayed` / `NotPlayingMission` / `GameOver`. The card is a `ResistanceMissionCardKind` stored in `ResistancePlayer.MissionCard` (an int; `Fail` 0 and `Success` 1 match the boolean it replaced, so old rows read unchanged, and the enum is only appended to) and never sent; the DTO has only `playedMissionPlayerIds`, `yourMissionCard` and `requiredFails`.
- The last card resolves the mission in the same save (`ResistanceFlow.ResolveMission` asks `ResistanceMissionRules.HasSucceeded`, the one pure function from the cards and the required fails to the result), appends a `ResistanceMissionResults` row (`missionResults` in the DTO: number, succeeded, fail count) and ends the game at 3 successes or 3 failures (with the Assassin module the third success opens the `Assassination` phase instead, see Assassin). Otherwise the phase is `MissionResult` until "Dalej" (`ContinueAsync`, valid only in `MissionResult`) passes the lead and starts the next mission.
- UI: `ResistanceMissionPanel` in `ResistancePlayerView`; results on `ResistanceMissionBoard`; `ResistanceMissionCards` shows a finished mission's Success/Fail/Reverse cards without names until "Dalej"; the "Dalej" button is for the leader (`ResistancePlayerView`) and managers (`ResistanceManagerControls`).

### Restart

- `POST restart` (host or admin) sends a finished game back to the open lobby with the same players and rules snapshot. `ResistanceGame.Restart` needs `Phase == GameOver`, or `Assassination` so an absent Assassin never strands a game (409 `NotOver`; 409 `NotStarted` before the start; 404 without a game), clears mission results, votes, team, cards, roles and leader through `ResistanceDealer.Reset` (mission 1, no rejections, no winner, seat releases cleared) and sets `StartedAt` to null.
- The lobby rules apply again: more players can join (the game stays open), plot cards can be switched and "Start game" deals again. `SetPlotCardsAsync` is allowed until the game starts (open or not); refreshing the rules still needs a game that is not open. UI: "Restart game" in `ResistanceManagerControls`, only in `GameOver` and `Assassination`.

## Plot cards (add-on)

All nine plot cards are playable.

### Dealing

- `ResistanceRules.PlotCardsEnabled` (default off, kept by `RefreshRulesAsync`) is switched by `PUT rules/plot-cards` (host or admin, 409 `PlotCardsLocked` once the game has started, so it can be switched while the game is open; the "Enable Plot cards" checkbox in the "Game settings" dialog, `ResistanceGameSettings`).
- `PlotDeck` is the 15-card deck; `PlotCardsPerRound` is 1 for 5-6 players, 2 for 7-8, 3 for 9-10. `ResistancePlotCard` rows (`Location` Deck/Drawn/Hand, `DeckOrder`, `HolderPlayerId`) are built and shuffled by `ResistanceDealer.BuildPlotDeck` on `Deal`.
- `ResistanceFlow.BeginMission` draws at the start of each mission (not after a rejected vote) and enters `DealingCards`; `SelectTeamAsync` answers 409 `CardsNotDealt` until the leader deals.
- `PUT cards/deal` (`{assignments:[{cardId,playerId}]}`, leader only) gives every drawn card except Establish Confidence (which stays with the leader) to another player.
- `ToDto` gives `yourPlotCards` only to their holder and public `plotCardCounts` (hand sizes). UI: `ResistancePlotDealer`, `ResistancePlotHand`, the count badge in `ResistancePlayerMarks`; the TV tab blanks `yourPlotCards`.

### Common rules for the windows

`LeaderWindow`, `ConfidenceWindow` and `PeekWindow` share one mechanism:

- A window opens whenever any playable card exists (`ResistancePlotCardQueries.HasPlayableCards`: a card in a hand, Opinion Maker excluded), whatever it is, so the window never tells which card is out there and the UI names no card to non-holders.
- Everyone confirms with `PUT leader-window/pass` (`ResistancePlayer.PassedLeaderWindow`; joined players only, 403 `NotPlayer`; 409 `CardNotPlayableNow` outside a window). Nobody learns who holds a card, only that one exists. The public `leaderWindowPassedPlayerIds` says who confirmed; when all did, `AfterWindow` moves on.
- A holder instead plays the card with its own endpoint. UI: `ResistanceLeaderWindow` serves the leader and confidence windows.

### Opinion Maker

- Dealing it puts the card `InPlay` (face up for everyone, auto-played; hand counts exclude it). `ResistancePlotCardQueries.OpinionMakerIds` lists the holders. While one has not voted, `VoteAsync` answers 409 `OpinionMakersFirst` to everybody else, and an Opinion Maker's own vote is final (409 `VoteLocked`; two holders vote independently and the others unlock when both have).
- The DTO has public `opinionMakerPlayerIds` and `opinionMakerVotes` (filled once every holder has voted) and `ResistancePlotCardDto.inPlay`. The vote panel waits and locks accordingly; the marks show a "Kreator opinii" badge plus the revealed vote.
- On the TV layout `ResistancePlayers` takes a `beside` slot (a card on the side of the seat facing the board), where `ResistanceTvBoard` shows `PlotOpinionMakerCardIcon` next to each holder; while the phase is `Voting` its "Głosy" section (`ResistanceVoteCards`) already shows `opinionMakerVotes`, the others joining once everybody has voted.

### Immediate cards

Overheard Conversation, Establish Confidence and Open Up (`ResistancePlotCardQueries.IsImmediate`) are played at once.

- After the deal `ResistanceFlow.AfterDeal` enters `ResolvingCards` when any is in a hand (else `SelectingTeam`); `SelectTeamAsync` answers 409 `CardsNotDealt` until all are done. They are played in parallel, in any order, and none can be declined.
- `PUT cards/{id}/play` (`{targetPlayerId}`, holder only): a neighbour by `Order` (wrapping) for Overheard Conversation, any other player for the rest (Open Up may target the leader; the leader plays Establish Confidence, which stays in their hand, on someone else). Errors: 403 `NotYourCard`, 404 `UnknownCard`, 409 `CardState` / `NotResolving`, 400 `InvalidTarget`. The card becomes `Played` with `TargetPlayerId`, `PlayedAt` and `PlayedInMission`.
- `PUT cards/{id}/confirm` is for the viewer only (`ResistancePlotCardQueries.Viewer`: the holder of Overheard Conversation, otherwise the target); the last confirmation of the round sets `SelectingTeam` in the same save.
- The DTO has a public log `playedPlotCards` (newest first, kept for the whole game, no identity cards in it) and the private `yourReveals` (`ResistancePlotCardQueries.Revealed`: the neighbour's role for the holder of Overheard Conversation, the holder's role for the target of the others) until the viewer confirms; the TV tab blanks `yourReveals`.
- UI: `ResistancePlotPlayer` (target picker, "Widziałem/am"); `ResistancePlotLog` under the phase banner (scrolls past 3 rows, `max-h-[4.25rem]`). The host and admins get a "Hide log" / "Show log" button in `ResistanceManagerControls` (phone Controls panel and TV nav alike), shown only once a card was played; the choice is `partyking.resistanceLogHidden` in `localStorage`, read by `Resistance`, which then leaves the log out of the shared `banner`.

### In the Spotlight

- The same `PUT cards/{id}/play`, but only in `ConfidenceWindow` (409 `NotPlayingMission` otherwise). It uses the same single confirmation stop as No Confidence: after an approved vote with any playable card in a hand everyone confirms once, or the holder names the forced player instead. The mission cards answer `NotPlaying` until the window ends.
- The target is another team member (400 `InvalidTarget`), once per mission (409 `CardState`). The card becomes `Played` with the target and `PlayedInMission`, already confirmed, so `UnconfirmedCards` (immediate cards only) ignores it.
- A No Confidence played afterwards cancels the team, so an In the Spotlight played in that window goes back to its holder's hand and out of the log.
- `ResistancePlotCardQueries.OpenMissionPlayerId` finds the forced player of the current mission; the DTO has the public `openMissionPlayerId` and, once they played, `openMissionCard`. UI: `ResistanceSpotlightPlayer` in `ResistancePlayerView`; the phase line names the forced player and their open card.

### Take Responsibility

- `PUT cards/{id}/take` (`{targetPlayerId, takeOpinionMaker}`, holder only) is `ResistanceGame.TakeResponsibility`. Errors: 403 `NotYourCard`, 404 `UnknownCard`, 409 `CardState`; 409 `CardNotPlayableNow` in any phase but `SelectingTeam` / `PlayingMission` / `PeekWindow` / `MissionResult` (never mid-vote); 400 `InvalidTarget` for yourself or an unknown player.
- The candidates are the target's face-up Opinion Maker and a random card from their hand. With both, `takeOpinionMaker` must say which (400 `ChoiceRequired`; the UI knows both from the public `opinionMakerPlayerIds` and `plotCardCounts`); with one the server takes it; with none the card is lost.
- The taken card only changes `HolderPlayerId` (an Opinion Maker stays `InPlay`, so `OpinionMakerIds` follows it); the played card is logged with the target, already confirmed. Nobody is told which hand card went; the taker sees it in their own hand. UI: `ResistanceTakeResponsibility`.

### Strong Leader (`LeaderWindow`)

- Opens at the start of a mission before the leader draws (`ResistanceGame.LeaderWindowBeforeDraw`, then `AfterLeaderWindow` draws) and after a rejected team before the new leader picks.
- The holder calls `PUT cards/{id}/take-lead` (403 `NotYourCard`, 404 `UnknownCard`, 409 `CardState` / `CardNotPlayableNow`, 400 `InvalidTarget` for the leader): the card is logged `Played` (target = the ousted leader, already confirmed), the lead moves and the window ends.
- A window cannot reopen without a vote resolving in between, which is the card's "next one only after the next vote" rule.

### No Confidence (`ConfidenceWindow`)

- Opens in `ResolveVotes` when a team is approved while any playable card is in a hand (otherwise the mission starts at once). `RejectedTeams` is not reset until the window ends; when everyone confirmed, `AfterWindow` starts the mission.
- The holder calls `PUT cards/{id}/no-confidence` (`ResistanceGame.PlayNoConfidence`; 403 `NotYourCard`, 404 `UnknownCard`, 409 `CardState` / `CardNotPlayableNow`): the card is logged `Played` (target = the leader whose team was cancelled) and `RejectTeam` runs, the same path as a lost vote (count +1; the fifth ends the game for the spies; else the lead passes, the team clears and a leader window may open).

### Keeping a Close Eye on You (`PeekWindow`)

- The last mission card resolves the mission (the result is public at once). When any playable card is in a hand the phase is `PeekWindow` instead of `MissionResult` and "Dalej" stays hidden; when everyone confirmed, `AfterWindow` sets `MissionResult`.
- The mission cards stay in `ResistancePlayer.MissionCard` until "Dalej". `PUT cards/{id}/peek` (`{targetPlayerId}`, holder only) is `ResistanceGame.PeekMissionCard`. Errors: 403 `NotYourCard`, 404 `UnknownCard`, 409 `CardState`, 409 `WrongPhase` / `CardNotPlayableNow` outside `PeekWindow`; 400 `InvalidTarget` for your own card, a player who played no card, or a player whose card the caller already looked at (a different holder may look at the same card; `ResistancePlotCardQueries.CanPeek`).
- The play is public (the log names holder and target, `Played`, already confirmed); the card seen is the private `yourPeeks` (`ResistancePlotCardQueries.PeekedCards`, only in `MissionResult`, blanked in the TV tab).
- A mission that ends the game leaves no window to peek (`GameOver`, 409 `GameOver`), and "Dalej" clears the cards, so a peek must happen before it. UI: `ResistanceCloseEye`.

## Inquisitor (module)

The Hostile Intent module; rules in `resistance-rules.md`. Off by default.

- `ResistanceRules.InquisitorEnabled` is switched by `PUT rules/inquisitor` (host or admin, 409 `RulesLocked` once the game has started, so it can be switched while the game is open; the "Enable Inquisitor" checkbox in "Game settings"). `Clone(plotCardsEnabled, inquisitorEnabled)` keeps the other flag, `RefreshRules` keeps both.
- **Token**: `ResistanceDealer.Deal` gives it to the player at `Order - 1` (wrapping) from the random first leader, our reading of "to the right of the first leader" (the lead passes to `Order + 1`). `ResistanceGame.InquisitorPlayerId` is the holder; `ResistancePlayer.WasInquisitor` marks everybody who held it (the first holder too), and those players cannot be examined. `Restart` clears both through `ResistanceDealer.Reset`.
- **Phase**: `ResistanceFlow.AfterMissionResolved` runs where a resolved mission used to set `MissionResult`: after the peek window ends (`AfterWindow`) or at once without a playable card. It enters `Inquisition` for missions 2 to 4 when the module is on; a mission that ends the game never gets there, and mission 5 has none. `Inquisition` is not a confirmation window (`IsConfirmationWindow` leaves it out) and `Take Responsibility` is not allowed in it (explicit allow-list).
- **Flow**: `PUT inquisitor/examine` (`{targetPlayerId}`, `ResistanceGame.Examine`) by the holder: the token passes to the target at once (public), `InquisitionExaminerPlayerId` remembers the examiner. `PUT inquisitor/confirm` (`ConfirmInquisition`) by that examiner clears it and sets `MissionResult`, so "Dalej" stays hidden until then. The examined player does nothing; there is no escape hatch for an absent holder (the host frees the seat, as in the plot-card windows). Errors: 403 `NotInquisitor`, 409 `NotInquisition` / `AlreadyExamined` / `NotExamined`, 400 `InvalidTarget` (yourself, a past holder, or an unknown player).
- **Views**: public `inquisitorPlayerId`, `pastInquisitorPlayerIds`, `inquisitionExaminerPlayerId`, `inquisitionExaminedPlayerId` and `rules.inquisitorEnabled`; the private `yourInquisition` (`{playerId, role}`) goes only to the examiner while the phase is `Inquisition` and is computed from `Role`, so nothing secret is stored and a seat takeover is safe. The TV tab blanks it. The mission's `yourPeeks` stay visible during `Inquisition`.
- **Event**: `ResistanceInquisitorTokenPassed(from, to)` carries who, never the loyalty.
- **UI**: `ResistanceInquisitor` (picker, then the loyalty with a note that nobody can check it, then "I've seen it"; others see nothing), a violet "Inquisitor" badge in `ResistancePlayerMarks`, the `InquisitorCardIcon` token card beside the holder's seat on the TV board (next to the Opinion Maker card when the same player has both), the `Inquisition` line in `resistancePhase.ts` (names the holder and the examined player, never the loyalty) and an "Inquisitor (module)" section in the rules dialog. `ResistanceTvBoard` keeps the mission cards visible during the phase.

## Blind Spies (variant)

The spies do not get to know each other (the rules' "skip the Spies Reveal step"). Nothing server-side stops them from talking; it is a table agreement.

- `ResistanceRules.BlindSpiesEnabled` is switched by `PUT rules/blind-spies` (host or admin, 409 `RulesLocked` once the game has started, so it can be switched while the game is open; the "Enable Blind Spies" checkbox in "Game settings"). `Clone(.., blindSpiesEnabled)` keeps the flag, `RefreshRules` keeps all four module flags. The rules are an owned JSON column, so a new rules property needs a migration only to move the column default (`AddBlindSpies`); old stored rules read with the flag off.
- **Who knows whom**: `ResistanceKnowledge.KnowsSpy(game, viewer, target)` is the one place that answers "does the viewer know the target is a spy"; `ResistanceGameViewBuilder.BuildFellowSpies` asks it for every player. It reads the sides through `ResistanceKnowledge.Loyalty(player)` (the current allegiance, see Allegiance and character below) and leaves out a hidden spy Reverser (see Reverser). Later modules that change who knows whom (Commander, Chiefs, Deep Agent) extend that function; the Defector already did, and `ResistanceGameBlindSpiesTests.KnowsSpy_EveryViewerAndTarget` pins the whole viewer x target table for each setting.
- **Views**: a spy gets `fellowSpies: []` (not `null`, which stays for everybody who is not a spy) and everybody gets `rules.blindSpiesEnabled`. At `GameOver` `revealedRoles` still shows everyone. The Inquisitor and the plot cards that reveal a loyalty are unaffected.
- **UI**: `ResistanceRoleCard` takes `blindSpies` and shows "Blind Spies: you do not know who the other spies are." in place of the list; a "Blind Spies (variant)" section in the rules dialog.
- No new event: the switch raises `ResistanceChanged` only.

## Allegiance and character

A player has two separate things: the **allegiance** (`ResistancePlayer.Role`, `Resistance` or `Spy`; the side they are on right now, which decides the win checks and `MustSucceed`) and the **character** (`ResistancePlayer.Character`, dealt once and never changed). Only the Defector changes the allegiance during the game (see Defector). Anything that shows a side to somebody (`yourRole`, `revealedRoles`, the identity cards of the plot cards, the Inquisitor, `KnowsSpy`) reads it through `ResistanceKnowledge.Loyalty(player)`, never the character and never `Role` directly, so the modules that change it need one change. Rule checks in the Domain (`MustSucceed`, the win checks) read `Role` as the current allegiance.

## Reverser (module)

The rules allow one or two Reversers, so the host chooses which sides get one (`ResistanceRules.ReverserSides`: `Both`, the default, `Resistance` or `Spy`). A Reverser on the mission team holds a third card, Reverse, which turns the result of the mission around.

- `ResistanceRules.ReverserEnabled` is switched by `PUT rules/reverser` (`{enabled, sides?, spyKnowsSpies?}`; an omitted `sides` or `spyKnowsSpies` keeps the choice; host or admin, 409 `RulesLocked` once the game has started; "Enable Reverser", a "Who gets a Reverser" select and a "Spy Reverser knows the other spies" checkbox, the last two enabled only while the module is on, in "Game settings"). `Clone(.., reverserEnabled, reverserSides, reverserSpyKnowsSpies)` and `RefreshRules` keep all three; migration `AddReverser` adds `ResistancePlayers.Character` (int, default 0) and moves the rules default (`ReverserSides` is stored by number, `Both` is 0). `rules.reverserSides` and `rules.reverserSpyKnowsSpies` are public. The mission card column did not change (see `PUT mission`).
- **Character**: `ResistancePlayer.Character` (`ResistanceCharacter`: `Standard`, `Reverser`) is dealt in `ResistanceDealer.Deal` (the first spy and/or the first resistance member of the shuffle, as `ReverserSides` says) and cleared by `Reset`. `Role` is the allegiance (see Allegiance and character).
- **Result**: `ResistanceMissionRules.HasSucceeded(cards, requiredFails)`: the mission fails without Reverse cards when the Fail cards reach `requiredFails`, and an odd number of Reverse cards turns that around (two cancel out). Decision where the rule text and formula disagree: on a mission that needs two Fails (7+ players, mission 4), one Fail plus one Reverse is a **failure**, because the single Fail alone would not have failed it.
- **Cards**: Reverse only from a `Reverser` (`NotReverser`, 403); a resistance member never plays Fail (`MustSucceed`) and a spy Reverser plays Success or Reverse, never Fail (`ReverserCannotFail`, 403). A Reverse card is private like the others, but `yourMissionCard`, `openMissionCard` (In the Spotlight) and the peeks of Keeping a Close Eye show the real kind, so an open or peeked Reverse tells who the Reverser is (that is the physical game too).
- **Played cards are public**: once the mission is resolved the cards are shown as when they are revealed shuffled at the table, without who played them. `ResistanceMissionResult` stores `FailCount` and `ReverseCount` (migration `AddMissionResultReverseCount`; 0 for old rows and without the module), the DTO has both (`reverseCount`), `ResistanceMissionCompleted` carries both, the phase line adds "(Reverse cards: N)" and the TV `ResistanceMissionCards` show the Fail cards, then the Reverse cards, then the Success cards (an In the Spotlight card first, with the name). Who is a Reverser stays secret.
- **Views**: `yourCharacter` is the caller's own character, only with the module on and the game started (null otherwise, and blanked for `?tv=1` like `yourRole`); `revealedRoles` carries `character` at `GameOver` (the player marks then show a "Reverser" badge); `rules.reverserEnabled` is public. Nobody learns another player's character; with `reverserSpyKnowsSpies` on (the default) `KnowsSpy` is unchanged (a Reverser is just a spy to the other spies).
- **UI**: `ResistanceMissionPanel` shows `MissionReverseCardIcon` to everyone on the team while the module is on (so having the card tells nothing) and enables it only for a Reverser, and disables Fail for a spy Reverser; `ResistanceRoleCard` tells a Reverser so and shows the `ReverserCardIcon` character card beside the role card; "Reverser (module)" in the rules dialog. `missionCardKeys.ts` maps a card to its translation key.
- Not combined yet with Rogue Agent, Hunter 7+ or Sergeant (special mission cards) or Trapper (not addressed by the rules): when those exist, reject the combination in the rules validation.
- **Spy Reverser and the reveal** (the optional rule, `ResistanceRules.ReverserSpyKnowsSpies`, `true` by default, also for rules saved before it existed, because the JSON property is missing there and the initializer applies; migration `AddReverserSpyKnowsSpies` only moves the rules default): when off, a spy Reverser keeps their eyes closed in the reveal, so they know no spy and no spy knows them. `ResistanceKnowledge.IsHiddenReverserSpy` decides it and `KnowsSpy` returns false for such a viewer or target. Their `fellowSpies` is `[]` (like Blind Spies) and the other spies' lists leave them out, so a spy cannot tell from the list that there is a hidden Reverser. The role card tells the hidden spy so (`hiddenReverserSpy`). The setting does nothing while the module is off or when only the Resistance gets a Reverser. A decision: symmetric, as at the table; an asymmetric variant (the Reverser sees the spies but is not seen) is not offered.

## Defector (module)

One Defector on each side, dealt after the Reverser. At the start of the missions 3, 4 and 5 one card of a shuffled switch deck is flipped for everybody; on Change Allegiance both Defectors change sides.

- `ResistanceRules.DefectorEnabled` and `DefectorsKnowEachOther` (both off by default) are switched by `PUT rules/defector` (`{enabled, knowEachOther?}`, an omitted `knowEachOther` keeps the choice; host or admin, 409 `RulesLocked` once the game has started; "Enable Defectors" and "The Defectors know each other" in "Game settings", the second enabled only while the module is on). `Clone(.., defectorEnabled, defectorsKnowEachOther)` and `RefreshRules` keep both; migration `AddDefector` moves the rules default and adds `ResistanceGames.DefectorDeck`. `ResistanceGame.Defector.cs` holds `SetDefector` (`DefectorLocked`).
- **Dealing** (`ResistanceDealer.DealDefectors`, after the Reverser, so a game without Defectors deals as before): the first spy and the first resistance member of the shuffle who still have no character get `ResistanceCharacter.Defector`, then the deck is shuffled. A side has at least two spies and three resistance members and a Reverser takes at most one per side, so one is always left.
- **Deck**: `ResistanceGame.DefectorDeck` is a string, one character per card in the order of flipping (`N` No Change, `C` Change Allegiance; three and two), secret and never sent. It is cleared by `Reset`. `ResistanceGame.DefectorFlips` is the public part: the first `MissionNumber - 2` cards, because a card is flipped exactly when a mission begins and the number only advances with it. Nothing else records a flip, so there is no event; the push is the usual `ResistanceChanged`.
- **Flip**: `ResistanceFlow.BeginMission` calls `FlipDefectorCard` first. A rejected team does not begin a mission (it goes `RejectTeam`, not `BeginMission`), so it flips nothing; mission 1 and 2 flip nothing. On `C` both Defectors' `Role` is inverted, so `MustSucceed`, the win checks, `yourRole`, the identity cards and the Inquisitor follow at once; `Character` stays.
- **Who knows whom** (decision, from the table: the spy Defector does not open their eyes in the reveal but shows a thumb): `ResistanceKnowledge.KnowsSpy` returns false for a Defector viewer, so a Defector knows no spy, whichever side they are on now. A Defector who started as a resistance member is never known to the spies (`IsUnknownDefector`: a Defector whose current side matches the parity of the switches so far tells where they started, `DefectorsSwitched`); the one who started as a spy is known to the other spies exactly while they are spies. So after a switch the spies' lists lose the former spy Defector and do not gain the new one, and after the second switch the first one is listed again. `ResistanceGameDefectorTests.KnowsSpy_EveryViewerAndTarget_BeforeAndAfterTheSwitches` pins the whole viewer x target table for 0, 1 and 2 switches.
- **Variant**: with `DefectorsKnowEachOther` each Defector gets the other's id as `fellowDefectorId` (`ResistanceKnowledge.KnowsDefector`), whatever side each is on.
- **Views**: `yourCharacter` is sent while Reverser or Defector is on (only the caller's own); `rules.defectorEnabled`, `rules.defectorsKnowEachOther` and `defectorFlips` (true = Change Allegiance) are public; `revealedRoles` at `GameOver` carries the final allegiance and the character (a "Defector" badge). The flips are public by decision (the PDF only says "flip one card"): everybody sees that a switch happened, nobody learns who the Defectors are. `fellowDefectorId` and `yourCharacter` are blanked for `?tv=1`.
- **UI**: the mission board draws each flipped switch card (`DefectorSwitchCardFace` in `ResistanceIcons.tsx`, a Resistance and a spy figure with swap arrows or an equals sign) in the upper left corner of the disc of its mission (3 to 5), with a tooltip that says what it did; the card has the accessible name "Mission 3: No Change" (`MissionBoardIcon` takes `defectorFlips`, the boards pass `game.defectorFlips`, which the server leaves empty while the module is off), and the latest card is drawn again beside the phase banner (`ResistancePhaseBanner`, `defectorFlips`, named "Latest switch card (mission N): ..."), because a phone player on their own tab does not see the board; `ResistanceRoleCard` tells a Defector so (and to look at the card again after each flip), names the other Defector with the variant and tells a spy Defector that they know no spy instead of listing spies; "Defectors (module)" in the rules dialog. `ResistanceRoleCard` also shows the `DefectorCardIcon` character card (a figure split into the Resistance and the spy side) beside the role card of a Defector.
- Not combined yet with Rogue Agent or the Chiefs; Hunter does not exist yet. The Deep Agent will extend `KnowsSpy`/`KnowsAbout`; the Hunter's mission results will need the final allegiance, not the starting one. The Defector is rejected together with the Assassin (see Assassin).

## Assassin (module)

The Hidden Agenda module: a Commander and an Assassin, plus four optional characters (Body Guard, Deep Cover, Blind Spy, False Commander). Off by default (rules in `resistance-rules.md`).

- `ResistanceRules.AssassinEnabled` is switched by `PUT rules/assassin` (`{enabled, bodyGuard?, deepCover?, blindSpy?, falseCommander?}`; an omitted option keeps the choice, switching the module off switches all options off; host or admin, 409 `RulesLocked` once the game has started; "Enable Assassin" and four option checkboxes in "Game settings", the options enabled only while the module is on). `Clone(..)` and `RefreshRules` keep all five flags; migrations `AddAssassin` (rules default, `ResistanceGames.AssassinationTargetPlayerId`) and `AddAssassinCharacters` (rules default). `ResistanceGame.Assassin.cs` holds `SetAssassin`, `Assassinate` and the start check.
- **Combinations** (decision): the module is rejected together with the Defector, the Reverser and Blind Spies, both ways (`SetAssassin(true)` while one is on, and each of their switches while the Assassin is on, answer 409 `Resistance.AssassinConflict`). The UI greys the checkboxes out in those cases. Inquisitor and Plot cards combine.
- **Dealing** (`ResistanceDealer.DealAssassin`, after the Defectors): the first spy of the shuffle who is still `Standard` becomes the Assassin and the first resistance member the Commander, with no extra random draw, so a game without the module deals exactly as before (the seeded e2e deals do not move). `Character` is `Commander` or `Assassin`; `Reset` clears them and the target.
- **Optional characters** (dealt right after the pair by `DealAssassin`, each the first `Standard` player of its side in the shuffle, still without an extra draw): the Body Guard (resistance), Deep Cover, the Blind Spy and the False Commander (spies). They only count while the module is on (a flag left over from a switched-off module is ignored; the setter clears them anyway).
- **Check at the start** (`ResistanceGame.AssassinCharactersFailure`, run by `Start` before the deal, because the player count is only known then): the Assassin takes one spy seat, so Deep Cover + Blind Spy + False Commander may be at most `spies - 1` (5 and 6 players: one; 7 to 9: two; 10: three), else 409 `TooManySpyCharacters`; with exactly 5 players a Body Guard needs Deep Cover or the False Commander, else 409 `BodyGuardNeedsCover` (rule from the PDF). The UI makes the same check (`assassinCharactersProblem`) to warn in the settings dialog and to stop "Start game" with a localized message; when the server still refuses a start (409) the page appends the server's reason to the generic "Could not start the game."
- **Who knows whom**: `ResistanceKnowledge.KnowsSpy` returns true for a Commander viewer and every spy target except Deep Cover, so `fellowSpies` also goes to the Commander (the role card shows it as "Spies you know"). The Blind Spy knows no spy and no spy knows them (the Commander does see them: the Blind Spy only skips the spies' reveal). Deep Cover and the False Commander are ordinary spies to the other spies. `ResistanceKnowledge.KnowsCommander` gives the Body Guard the Commander and the False Commander alike, sent as the private `yourCommanderCandidates` (null for everybody else, and blanked for `?tv=1`). Nobody else knows the Commander; the Assassin knows the other spies as any spy does. `ResistanceGameBlindSpiesTests`-style viewer x target table: `ResistanceGameAssassinTests.KnowsSpy_EveryViewerAndTarget`.
- **The third success** (`ResistanceFlow.ResolveMission`): with the module on and three successes the phase is `Assassination`, `Winner` stays null, no `ResistanceGameOver` is published, and nothing else happens in between (no peek window, no Inquisition), as after a mission that ends the game. Three failures still end the game for the spies; five rejected teams too.
- **The guess**: `PUT assassin/target` (`{targetPlayerId}`, `ResistanceGame.Assassinate`) is only for the Assassin: 403 `NotAssassin` (also for the host and admins who are not the Assassin), 409 `NotAssassination` outside the phase (`GameOver` after the guess), 400 `InvalidTarget` for the Assassin themselves or an unknown player (anyone else may be named, a spy included). The Commander named means `Winner = Spy`, else `Resistance`; the phase becomes `GameOver`, `AssassinationTargetPlayerId` is stored and `ResistanceAssassinated(assassin, target)` and `ResistanceGameOver` are published (no secrets: the game is over). The other spies talk it over outside the app; there is no vote.
- **Other actions** in `Assassination` are refused by their own phase checks. `Restart` is allowed from `Assassination`, so a host can end a game that waits for an absent Assassin (seat takeover works too: the character lives on the seat).
- **Views**: `yourCharacter` is sent while the module is on (only the caller's own); `rules.assassinEnabled`, the four option flags and `assassinationTargetPlayerId` are public; `winner` and `revealedRoles` stay null during `Assassination` and appear at `GameOver` (with `commander`/`assassin` characters, shown as badges). The TV tab blanks `yourCharacter` and `fellowSpies` as for every module.
- **UI**: `ResistanceAssassin` (a picker of the other players and "Name the Commander", only for the Assassin during the phase); the `Assassination` line in `resistancePhase.ts` (the same for everybody and never naming the viewer) and the "the Assassin named X, who is / is not the Commander" reason at game over; `ResistanceRoleCard` tells each of the six characters so and shows `CommanderCardIcon`, `AssassinCardIcon`, `BodyGuardCardIcon` (with the list of possible Commanders), `DeepCoverCardIcon`, `BlindSpyCardIcon` or `FalseCommanderCardIcon` beside the role card (all in the icon guide, group "Assassin (module)"; a Blind Spy gets a note instead of the spies list); "Assassin (module)" in the rules dialog.

## Presence (TV view)

The TV shows a dot per seat (green online, grey offline, the seat dimmed) for players who have the Resistance page open.

- `IGamePresence` (`Application/Realtime`, singleton, in memory, generic by `GameKind` but pushing only for Resistance) keeps a set of hub connection ids per `(kind, session, player)`. `ConnectAsync` pushes at once when the player comes online; `Disconnect` keeps them online for a 10 s grace (`GamePresence.DefaultGrace`, a cancelable `Task.Delay` per player, like `PlayerConnectionWatchdog`) before the offline push, so a reconnect or page change does not flicker. Nothing is cleaned up on session delete because every entry dies with its connection.
- `SessionHub` registers a connection only when the URL has `&presence=1` and the signed `cookie.partyKing.resistance` yields a player id (the player is never taken from the client). The TV tab shares that cookie, so `Resistance.tsx` sends the flag only for a view that is not the TV layout and not `?tv=1`. The dev persona reaches the hub through `&persona=`, which `DevPersonaMiddleware` reads on `/hubs/session`.
- The push is `ResistancePresenceChanged` with the whole `{onlinePlayerIds}` (`ResistancePresenceDto`) through `IResistanceNotifier.PresenceChangedAsync`, on its own topic `resistancePresence`, which only the TV layout follows (`RESISTANCE_TV_HUB_TOPICS`), so phones never refetch the game because someone's signal blinked.
- `GET presence` (`ResistancePresenceService`, host or admin) is the snapshot the TV loads and refetches after a reconnect (`useResistancePresence`; no data means no status shown yet).

## Seat takeover (returning to a started game)

A started game locks its players, and the player cookie is the only identity, so a player who lost it (a private tab on an iPhone closed by the system) could not return. The host or an admin releases the seat of an *offline* player and a guest claims it from the join page, without a new name.

- **Domain** (`ResistanceGame.Seats.cs`):
  - `SetSeatReleased(playerId, released, playerOnline)` fails with `NotStarted`, `UnknownSeat`, `ManagerSeat` (the seat of the host or of an admin) or `SeatOnline` (releasing a connected player); taking a release back is always allowed.
  - `ClaimSeat(playerId, playerOnline, newStamp)` fails with `SeatNotReleased` (an unknown, unreleased or manager seat alike) or `SeatOnline`; a claim ends the release and sets the stamp.
  - `ResistancePlayer.IsReclaimable` is the release (cleared by `ResistanceDealer.Reset`). `LobbyPlayer.IsAdminSeat` is set at join from `caller.IsAdmin` whatever name the admin typed (a guest who types "admin" has an ordinary seat). `IsManagerSeat` = host (`ProfileId`) or admin seat. `LobbyPlayer.ClaimStamp` (null until the first takeover; `IsHeldBy(stamp)`) cuts the old device off.
  - These columns exist on `ResistancePlayers` only (migration `ReclaimableSeats`; Ringo ignores them in `RingoPlayerConfiguration`, because Ringo has no secrets and no presence). Events: `ResistanceSeatReleaseChanged`, `ResistanceSeatClaimed`.
- **The stamp**: the player cookie holds `session:player[:stamp]` (`GameSeat(PlayerId, Stamp)` in `Application/Games/Services/Base`; `ISignedCookies.GrantGamePlayer` / `TryReadGamePlayer` take and return it; old cookies without a stamp still read). `GameCaller.PlayerStamp` carries it, and `GameLobby.PlayerOf` (so `IsPlayer`, `AccessAsync`, the views and `JoinAsync`) counts the id only when the stamp is the seat's; `GetLobbyAsync` does the same in its projection. Services read `caller.PlayerId` directly inside `RunAsPlayerAsync` lambdas, which is safe only because `AccessAsync` ran first for every non-manager; a manager's own seat is never released, so its stamp never changes.
- **Presence link**: `SessionHub` registers presence only when `IResistanceSeatService.HoldsSeatAsync` agrees, and `ResistanceSeatClaimedHandler` calls `IGamePresence.ForgetAsync`, so the old tab (still connected) cannot keep the seat online.
- **Service** (`ResistanceSeatService`, scoped): `GetClaimableAsync` (anyone who unlocked the session; released seats with no connected device, empty before the start), `SetReleasedAsync` (host or admin through the gate; presence is read inside the write lock), `ClaimAsync` (returns the new `GameSeat`; the controller grants the cookie) and `HoldsSeatAsync`.
- **Endpoints** (`ResistanceSeatsController`): `GET claimable-seats`, `PUT players/{id}/release` `{released}`, `POST claim` `{playerId}` (rate limit `session-join`).
- **Release stays, availability follows presence**: a released seat whose player is online again is hidden and refused, and becomes claimable again when they drop, without the host acting. A release has no timer and ends only by a claim, taking it back, or a restart. After a server restart presence is empty, so the host can release anyone, but no seat is claimable unless the host released it first, which protects a flaky connection.
- **Host**: `GameLobby.JoinAsync` returns a `GameSeat` and gives the session host their own seat back by `ProfileId` even in a started game (no stamp rotation; the host's cookies prove who they are; also for Ringo).
- **Pushes**: both events send `ResistanceLobbyChanged`, and `ResistanceChanged` through `Succeeded()`.
- **UI**: `ResistanceManagerControls` has "Free a seat" once started (`ResistanceSeatsDialog`: offline players with a Release / Take back button; the seats of the host and admins are not listed; presence from `useResistancePresence(sessionId, open)`). `GameJoin` takes an optional `returnToGame` (`ResistanceJoin` passes it) and for a started game shows the `GameSeatPicker` (seats from `useResistanceClaimableSeats`: SWR key `resistanceClaimableSeatsKey`, revalidated by the lobby pushes and polled every 10 s) and a "Rejoin as the host" button for the host; after a claim it revalidates the lobby and game keys like a join. A tab whose seat was taken over becomes an observer (`GET games/resistance` answers the observer view), and `Resistance` shows "no longer a player" with a link to the join page.

## Views and UI

- Pages: `ResistanceEntry` on the `Games` row shows "Create" or "Resume". `Resistance` (`/s/:sessionId/games/resistance`) is a shell (data, hub, dialogs, nav) over two layouts. `ResistanceJoin` (`.../resistance/join`) and `ResistanceInvite` mirror Ringo's. `ResistanceIconGuide` (`.../resistance/icons`, `sessionResistanceIconsPath`) is the icon guide: every icon the game draws with what it means, grouped into the base game and each module (Plot cards from `PLOT_CARDS`, so a new card appears with its name and effect). A button left of "Close" in the rules dialog opens it. **A new icon, card or token belongs in it**, in the group of its module (texts under `resistance.iconGuide`); `PlotCardIcon` and `TeamTokenIcon` are not drawn anywhere yet and are left out.
- Shared parts of the board: `MissionBoardIcon` for the players who joined (`missionBoardFor`: team sizes for 5-10 players from `CLAUDE.local.md`; the 5-player sizes are dimmed with a notice below 5), `ResistancePlayers` along the left, bottom and right margins (`seatPositions` from `ringoSeats.ts`, like Ringo; the board keeps to the middle 80%), the "Players" dialog (`ResistanceSettings`), an "i" button with the Polish rules (`resistanceRules.ts`) and, for admins, "Open the game". The host and admins get "Start game" (disabled below 5) and lose "Players" and "Open the game" once started. The phase banner (`ResistancePhaseBanner`) is in every view.
- **TV layout** (`ResistanceTvBoard`: board in the middle 80%, players around the edge, manager controls in the nav): used with `?tv=1` (host/admin only; ignored for guests) and by a host or admin who is not playing. In `?tv=1` the page hides the role, the "Ty" badge and the spy markers and blanks `yourPlayerId` / `yourRole` for the phase line, because the TV tab shares the player cookies of the same browser.
- **Phone layout** (everyone else): a joined player (host and admin included) has a `ResistanceViewSwitch` between the player view (`ResistancePlayerView`: role card; the default), the board view (`ResistanceCompactBoard`: full-width mission board with the players as a list, leader crown, "Ty") and the queue view (`ResistanceQueuePanel`). The choice is `partyking.resistanceView` (`player`, `board` or `queue`; `useResistanceView`; the old boolean `partyking.resistanceBoardView` = true still reads as the board) in `localStorage`; the TV tab never reads it. From 1024 px wide (`useMediaQuery`) a player always sees the player view on the left and the switch (Board / Queue only) picks the right column. Observers only get the board. The host and admins also get a collapsed "Controls" button that expands the same manager buttons as the TV nav (`ResistanceManagerControls`) plus an "Open TV view" link (new tab, `?tv=1`; the fallback when the browser blocks the second tab).
- **Phase description**: a line above the board (`resistancePhaseDescription` in `resistance/resistancePhase.ts`, Polish) says what phase the game is in and what to do next, depending on whether the viewer is a manager. It never names the viewer's role, since it stays visible while the card is face up.
- **Queue panel**: `ResistanceQueuePanel` is the session's music inside the game, for everyone who has the switch and, for the host and admins who are not playing (TV layout), behind a "Queue" button in the TV nav that opens a dialog. It shows `NowPlayingLine` (title and artist, or the YouTube video name, no art), the `Queue` form and list (anyone adds a song; `canRemove` for the host and admins) and, for the host and admins, `RemotePlayerControls`. Only the host gets the volume (written to `partyking.volume`, so it reaches `HostPlayer` in the music tab of the same browser). The music still plays in the host's tab on the session page: `OpenGamesMenu` opens games in a new tab so it keeps running, and following an in-tab link away from the session page stops it (the panel then shows "The host's player is not connected.").
