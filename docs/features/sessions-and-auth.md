## Sessions

- A `Session` has a GUID id, a unique short `Code` (from `SessionCodeGenerator`), a name defaulting to "New session" and a nullable `HostProfileId`. It owns one `QueueItem` queue (`QueueItem.SessionId`, cascade delete) and its own slideshow.
- `HostDisplayName` is not stored with the session: `SessionsRepository.GetAsync` / `GetAllAsync` read only the host's display name from the profile (never the profile with its refresh token) and hand it over with `WithHostDisplayName`.
- Only an admin creates or releases sessions (`/admin/sessions...`). The host or an admin renames a session, changes its password and deletes it at once (`DELETE /sessions/{id}`). Any guest with access can ask for the session to be deleted after a delay (`POST /sessions/{id}/deletion-request`, see "Scheduled deletion" below); only an admin can call that off. `GET /sessions` (id, code, name and only whether there is a host, `SessionListItemDto`: never who it is) and `GET /sessions/{id}` (with the host's name) are public. The admin panel lists the sessions with their hosts' names through `GET /admin/sessions` (admin only).

## Session password and QR join

### Password

- Every session has a mandatory password (`Session.PasswordHash`, PBKDF2 through `IPasswordHasher`, 4-100 characters), set by `POST /admin/sessions` and changed by the host or an admin through `PUT /sessions/{id}/password`.
- Everyone who joins, admins included, unlocks the session with `POST /sessions/{id}/join` (rate limited, 10 per minute per IP). It answers 401 for a wrong password and for an unknown session alike, and verifies against a dummy hash so timing doesn't tell them apart.
- `SessionAccessService.JoinAsync` returns an access stamp (hash of the password hash). `ISignedCookies.GrantSessionAccess` stores it in the signed `cookie.partyKing.sessions` cookie together with the session id (at most 20 sessions).
- `[RequireSessionAccess]` (`SessionAccessFilter`) checks the cookie against the route's `sessionId` and answers 401 on every session endpoint (`GET /sessions/{id}`, `/me`, `now-playing`, `songs` list/add/remove, `songs/next`, `tracks`, `host-login-urls`, `player/state`) and on the admin player endpoints (`admin/sessions/{id}/player/commands` and `songs/next`).
- Changing the password changes the stamp, so old unlocks stop working. `ChangePasswordAsync` returns the new stamp and the controller grants it to the caller again, so the host or admin who changed it stays unlocked.
- Release host is admin-only and needs no session password; an admin can also delete a session (`DELETE /admin/sessions/{id}`). Rename (`PATCH /sessions/{id}`) and change password are host-or-admin (`RenameAsync` / `ChangePasswordAsync` take the `SessionCaller` and answer Forbidden otherwise) and, being `[RequireSessionAccess]`, need the session unlocked, so an admin who doesn't know the password can't reset it (accepted).
- UI: `SessionPasswordForm` is shown on `/s/:sessionId` when `getSession` answers 401; the axios instance sends credentials on every call.

### Join with QR code

- The host and admins (`useViewerRole`) get a "Show QR code" button (`JoinQrCode`, MUI `Dialog`) on the session page.
- `POST /sessions/{id}/join-token` (`[RequireSessionAccess]`, 403 unless host or admin) returns a stateless token (`JoinTokenProtector`, Data Protection; it holds session id, access stamp and a 5-minute expiry; no DB table). The dialog shows a QR of `/s/{id}?join=<token>`, replaced 30 s before it expires.
- `MusicQueue` redeems `?join=` through `POST /sessions/{id}/join-with-token` (same `session-join` rate limit, plain 401 on any failure), which grants the same session cookie as `/join`, then strips the param.
- A token is reusable until it expires and can't be revoked individually, but changing the password changes the stamp and kills all of them.

## Session host (Spotify login)

- One host per session, and one Spotify account can host one session (unique index on `Session.HostProfileId`). Spotify profile ids are strings; `SpotifyProfile.DisplayName` is shown as "Current Host".
- **Flow**:
  1. `POST /sessions/{id}/host-login-urls` stores a short-lived `OAuthState` (the OAuth `state` parameter, single use) and returns the Spotify URL.
  2. Spotify redirects to the fixed `/callback`, which posts `{code, state}` to `POST /authenticate`.
  3. `SessionsRepository.TryClaimAsync` atomically claims the session: first account wins, others get 409, the current host logging in again is fine.
- An admin can release the host (`DELETE /admin/sessions/{id}/host`).
- **`OAuthState`**: `OAuthState.Issue(sessionId, now)` makes the 48-character hex id from 24 random bytes (kept in the Domain because how unguessable it is is part of the rule); `Lifetime` is 10 minutes; `IsExpired(now)` is true only after `ExpiresAt`; `SpotifyService` fills `now` from `IDateTimeProvider`. `IOAuthStatesRepository` is a Domain port: `AddAsync(state, now)` also forgets the states that expired before `now`; `TakeAsync(id)` returns and deletes the state, the delete deciding who took it, and returns an expired state too, so `AuthenticateByCodeAsync` asks `IsExpired` and an expired or replayed state is used up either way. Tests: `OAuthStateTests` (Domain), `OAuthStatesRepositoryTests`, `SpotifyServiceTests`.
- **`HostTokenProvider`** (singleton) caches and refreshes one access token per host profile, resolved through the session, and returns `Error.Unauthorized` when the refresh token is dead (the host logs in again; "I'm the host" in `SessionHeader`).
- **Playback state**: the host's browser reads `GET https://api.spotify.com/v1/me/player` (scope `user-read-playback-state`; hosts who logged in before it was added get a 403 and just see the normal button until they log in again). While the host has not started the player and the playing song is a Spotify track that this account has on another device (playing or paused), `HostPlayer` shows "Play here" instead of "Start the music" (`takeover.ts`), and `SpotifyPlayer` continues the song with `position_ms` in its `/me/player/play` call, so it starts at the other device's position as a single-track context.
- **Local dev**: the OAuth redirect URI uses `127.0.0.1`, so log in via `http://127.0.0.1:2137/...`, not `localhost` (the Vite dev server redirects `localhost` to `127.0.0.1`; the SameSite=Lax login cookies don't reach the API from a page opened via `localhost`). YouTube refuses to play embeds (player error 150) when the page's origin is an IP address such as `127.0.0.1`, so YouTube songs can't play in local dev; it goes away on a real domain.

## Cookies

- `cookie.partyKing.user` (the host's profile id) is signed with ASP.NET Data Protection in `SignedCookies`, so clients can't forge identities. Mind the names: `user` is the Spotify **host**; a login is the identity service's session cookie (see "Accounts"), which PartyKing never reads or writes. `cookie.partyKing.auth` holds the host's Spotify access token (set by the host handler when it is missing, and by the host login); `cookie.partyKing.sessions` the unlocks; `cookie.partyKing.demo` (signed, demo servers only) the demo sessions this browser started with their synthetic host profile ids, so a demo host can be restored after a newer start replaced `cookie.partyKing.user` (see `demo.md`); `cookie.partyKing.ringo` / `.resistance` the game players (see `../games/`).
- Cookies are HTTP, so `ISignedCookies`, `SignedCookies` and the cookie names (`CookieNames`) live in `PartyKing.API/Cookies`, and the scheme names (`SchemeNames`) and the two scheme handlers (`Authentication/Schemes`) in `PartyKing.API/Authentication`. Controllers, the hub and the authentication handlers call it (`GrantHost`, `GrantSpotifyAccessToken`, `GrantSessionAccess`, `GrantDemoSession` / `ReadDemoSessions`, `GrantGamePlayer`, `TryRead...`), never the services.
- The host scheme (`SchemeNames.Host`, `CookieAuthenticationHandler`) adds `NameIdentifier` (profile id) and `Authentication` (access token) claims; the account scheme (`SchemeNames.Account`, `AccountCookieAuthenticationHandler`) backs `[AuthorizeAccount]` (any signed-in account) and `[AuthorizeAdmin]` (the `Admin` role on top); it asks the identity service who the session cookie belongs to.

## Accounts (the identity service)

Users and admins are accounts of a separate service, `auth.talgrim.dev` (repo `talgrim/auth`, whose `plan.md` has the service side and the API contract). PartyKing keeps no accounts: it asks who the caller is. The same login works on `talgrim.dev`, `wip.talgrim.dev` and `notes.talgrim.dev`. What an account may do here: a **user** saves playlists of a session's queue (see `music.md`); an **admin** manages sessions. Registration, login, the password, "log out everywhere", deleting an account and the admin's list of users live in the identity service, not here. Plan and decisions: `docs/plans/shared-login.md`.

### The session cookie and the identity client

- The identity service sets one opaque cookie, `__Secure-talgrim.session` (`Domain=.talgrim.dev; Secure; HttpOnly; SameSite=Lax`), and a JS-readable hint cookie, `talgrim-signed-in`, that carries no identity. The browser sends the session cookie to `party.talgrim.dev` on its own; PartyKing forwards it and never reads or writes it. In Development the name is `talgrim.session` (the `__Secure-` prefix is dropped over plain HTTP) and the cookie has no `Domain`, so every port of `127.0.0.1` sees it.
- `IIdentityClient` (`Application/Ports`): `GetCallerAsync(cookieHeader, requiredRole, cancellationToken)` returns an `IdentityResult`: `Anonymous`, `Account(id, username, role)`, `Forbidden` (a role was required and the account lacks it) or `Unavailable`. Domain and Application know nothing of HTTP.
- `IdentityClient` (`Infrastructure/Identity`, a singleton) asks `GET {BaseUrl}api/session[?role=]` with **only** the session cookie (200 `{id, username, role}`, 401 anonymous, 403 forbidden; any other status, a timeout or an unreadable body is `Unavailable`). A request without the session cookie is `Anonymous` **without a call**, so guests, who have no account, cost nothing on the polled endpoints.
- Answers are cached in memory in a cache of its own (`IdentityCache`, at most 10 000 entries, keyed by a hash of the cookie value and the role): `Identity:CacheSeconds` (30) for an account, `NegativeCacheSeconds` (5) for anonymous and forbidden. `Unavailable` is never cached. While the identity service cannot be reached, an account answered within `StaleSeconds` (300) is still believed, so an outage does not log everybody out; nobody else can be answered. Freshness and the stale window are both checked against `IDateTimeProvider`, not left to the cache's eviction.
- Metrics (`IdentityMetrics`, meter `PartyKing.Infrastructure.Identity`): `partyking.identity.cache.hits`, `.calls` and `.call.duration` (tag `outcome`: account, anonymous, forbidden, unavailable) and `.stale`.
- Settings (`IdentityConfiguration`, section `Identity`): `Enabled` (true), `BaseUrl`, `CookieName`, `CacheSeconds`, `NegativeCacheSeconds`, `StaleSeconds`, `TimeoutSeconds` (3) and `WebhookSecret` (a secret). With `Enabled=false` (the demo) `RegisterIdentityInfrastructure` registers nothing and Application's `NullIdentityClient` stays: nobody is ever signed in and nothing is called.

### Authentication in the API

- `AccountCookieAuthenticationHandler` (scheme `SchemeNames.Account`): no session cookie means **no result** (and no call, and no metric); a rejected cookie fails (401); an account becomes a principal with `NameIdentifier` (the account id, a GUID), `Name` and `Role` claims. It always asks without `?role=`, so there is one cache entry per cookie, and the `Admin` policy checks the role claim. The answer is kept in `HttpContext.Items`, so a request asks once however many guards read it.
- **Outage is a 503, not a 401.** When the answer is `Unavailable` the handler fails the authentication and remembers why; its challenge then writes 503. The UI reads a 401 as "logged out" and would drop its hint. `ReadSessionCallerAsync` does not fail the request: a caller the identity service cannot vouch for is a plain guest there (an admin without a fresh cached answer loses admin rights on session endpoints for the length of the outage).
- `[AuthorizeAccount]`, `[AuthorizeAdmin]`, `HttpContext.ReadSessionCallerAsync` and `SessionCaller.IsAdmin` keep their names and meaning. **A signed-in user is not an admin**: `[AuthorizeAdmin]` is the `Admin` policy, and `IsAdmin` is set only for an account the identity service says is an `Admin`. A role change in the identity service shows within the cache time (30 s), no longer "after the next login". `AccountAuthenticationTests` pins this against the real wiring with a fake `IIdentityClient`.

### Integration events (the account deletion webhook)

- The identity service tells the other sites what happened to an account with **integration events**: it writes the event to an outbox in the transaction of the change and delivers it with a signed `POST /internal/events` (`InternalEventsController`; behind nginx `/api/internal/events`), again and again until it gets a 2xx, also across its restarts. The endpoint is public but signed, out of Swagger, limited to 16 KB and rate limited by `identity-webhook` (30 a minute per IP).
- The body is the envelope `{id, type, occurredAt, data}`; the headers are `X-Identity-Timestamp` (Unix seconds) and `X-Identity-Signature: sha256=<hex>`, the HMAC-SHA256 of `"{timestamp}.{body}"` under `Identity:WebhookSecret`, over the exact bytes of the body. The signature covers the body and not the path, so nginx removing `/api` needs no setting. `IdentityWebhookVerifier` refuses (401) a missing or wrong signature (compared in constant time), a body changed after signing, a timestamp more than 5 minutes off in either direction, and every call when no secret is configured. The controller reads the raw bytes before it parses anything.
- Answers: 204 once handled, also when there was nothing to do and for a type this app does not know (anything else makes the service retry); 401 unsigned or old; 400 for a signed body that is not an event (or an `account.deleted` without a valid `data.accountId`).
- `account.deleted` calls `ISavedPlaylistService.DeleteByOwnerAsync`, which deletes that owner's saved playlists (`ISavedPlaylistsRepository.DeleteByOwnerAsync`, one `ExecuteDelete`; the songs go with their playlist through the cascade). It is idempotent, so a repeated event `id` is harmless and no ids are stored. There is **no foreign key** from `SavedPlaylists.OwnerAccountId` to an accounts table any more (migration `MovedAccountsToIdentityService` dropped it and the `Accounts` table); the account ids are the same ones the accounts had before they moved. A new event type is a new branch in the controller.

### UI

- Every page has the account part of the header (`AccountMenu`). For a visitor it is two links, "Log in" and "Sign up", to `{identityUrl}/login?next=<this page>` and `/register?next=...`; signed in, the username with "Account settings" (a link to the identity service) and "Log out" (`POST {identityUrl}/api/logout`). `useAccount` asks `GET {identityUrl}/api/me` cross-origin with credentials; it asks when the identity service's hint cookie is there, when PartyKing's own localStorage hint is set (`partyking.accountHint`) or with `alwaysCheck` (the admin page). A 401 drops the localStorage hint. See `frontend.md`.
- `/admin` shows a link to the login when nobody is signed in, the "not an admin account" notice for a user and the panel for an admin, with a link to the identity service's list of users.
- The demo has no accounts: `AppHeader` hides the menu (and a demo runs with `Identity__Enabled=false`).

Tests: `IdentityClientTests`, `IdentityRegistrationTests` (Application), `AccountAuthenticationTests`, `InternalEventsControllerTests`, `DevPersonaMiddlewareTests` (Api), `SavedPlaylistsRepositoryTests` and `SavedPlaylistServiceTests` (deleting an owner's playlists), and the e2e spec `identity.spec.ts` with its fake identity service (`testing-e2e.md`).

## Dev personas

In Development and the e2e environment only (`IsDevelopmentOrE2e`), `DevPersonaMiddleware` (`PartyKing.API/Development`) lets one browser play several guests. The UI (`service/devPersona.ts`) keeps a tab's `?persona=<name>` in `sessionStorage` and sends it as `X-Dev-Persona`. Such a request is a plain guest (the host cookies and the identity service's session cookie hidden) with its own Ringo/Resistance player cookies (stored as `<cookie>.<persona>`), while the session unlock cookie stays shared. `OpenGamesMenu` and `GameInvite` carry the persona into the tabs they open. The hub reads it from `&persona=` on `/hubs/session`.

**All players in one tab** (`ResistanceDevPanels`, route `/dev/s/:sessionId/resistance`, registered in dev builds only, opened by the dev-only "Dev: all players" link in the Resistance navigation for the host and admins): picks 5 to 10 players, joins `dev-1`..`dev-N` through `gamesApi` (the optional `persona` argument sends `X-Dev-Persona` for that one call, so the page itself keeps the admin identity of the tab it was opened from), starts the game on request and shows one same-origin `<iframe>` per player (a grid of up to 2 rows, each panel scrolls on its own). A frame is `isDevEmbedded` (`window.self !== window.top`): it takes its persona from `?persona=` or else from its `window.name` (set by the page, survives a reload and an in-frame navigation that drops the query) and never reads or writes the tab's `sessionStorage`, which a same-origin frame shares with its parent. A frame also drops the language switcher and, in `Resistance`, the navigation, phase banner, board and queue, so it shows only the player's own view. The join needs the session unlocked in this browser (the unlock cookie is shared by personas) and, past 10 joins a minute, `RateLimiting__Disabled=true` on the API.

## Session aggregate, events and handlers

### Aggregate

- `Session` is an `AggregateRoot` with `internal set` properties. Actions: `Rename`, `ChangePassword`, `ClaimHost`, `Release`, `SetFallbackPlaylist`, `SetFallbackSavedPlaylist`, `ClearFallbackPlaylist`, `ScheduleDeletion(now, delay)` (`SessionDeletionScheduleOutcome`: `Scheduled`, or `AlreadyScheduled`, which keeps the first time so repeated requests cannot extend the delay) and `CancelDeletion` (`SessionDeletionCancelOutcome`: `Cancelled`, `NotScheduled`; the admin-only rule is above the Domain); queries `NextFallbackTrack`, `NextFallbackSavedSong` and `IsDueForDeletion(now)` (`DeletionScheduledAt <= now`). Inside `Session` the `FallbackPlaylistKind` enum members are written `Enums.FallbackPlaylistKind.X`, because the property of the same name hides the type. Id and time are arguments (the services fill them from `Guid.NewGuid()` and `IDateTimeProvider`).
- **Name rule**: `SessionNames` in Domain (trim, then at most 60 characters). `Session.Create(id, code, name, passwordHash, now)` falls back to "New session" for a blank name and refuses a long one with a `SessionCreation`. `Rename` returns a `SessionNameFailure` instead of throwing, and `ISessionsRepository.RenameAsync` a `SessionRenameResult`. `SessionNamePolicy` in Application only maps the failure to errors.
- **Password rule**: the `SessionPassword` value object (4-100 characters; `Create` returns a `SessionPasswordCreation`; `CanMatch` is the pre-hash length guard of `JoinAsync`). `Session.AccessStamp` / `AccessStampOf(hash)` / `IsUnlockedBy(stamp)` hold the stamp rule.

### Events

`SessionRenamed`, `SessionPasswordChanged` (no hash), `HostClaimed`, `HostReleased(PreviousHostProfileId)`, `SessionDeleted(HostProfileId, FallbackPlaylistId)` (a Spotify id only, a saved playlist has nothing to evict), `SessionDeletionScheduled(DeletionScheduledAt)` (raised once, a repeated request raises nothing) and `SessionDeletionCancelled`, `FallbackPlaylistChanged(Kind, PlaylistId, PreviousSpotifyPlaylistId)` (one event for both kinds; the previous id is there so the handler can evict the cached tracks of a Spotify playlist that was replaced, null when it was a saved one) and `FallbackPlaylistCleared(PreviousPlaylistId)` (raised by `Release` too, and never when there was no playlist; the id is null when a saved playlist was removed). In `Domain/Events/Sessions`.

### Scheduled deletion (`Application/Sessions`)

- Endpoints: `DELETE /sessions/{id}` (`[RequireSessionAccess]`, host or admin, 204; 403 for anyone else and in the demo), `POST /sessions/{id}/deletion-request` (`[RequireSessionAccess]`, any guest, 204 whether or not it was new, rate limited at 10 per hour per IP by the policy `session-deletion-request`) and `DELETE /admin/sessions/{id}/deletion-request` (`[AuthorizeAdmin]`, 204, also when nothing was scheduled). `SessionDto.DeletionScheduledAt` (UTC `DateTimeOffset`, null when none) is how the UI knows; the public list (`SessionListItemDto`) does not carry it. `SessionMappings` turns the stored time into UTC explicitly, because a database read leaves its kind unspecified.
- `SessionDeletionWorker` (API, `Workers/`) runs `IScheduledSessionDeletionSweep` at startup and then every `SweepIntervalSeconds`. Unlike the demo sweep it is registered on every server, the demo included. It and `DemoSessionCleanupWorker` share `PeriodicSweepWorker` (one sweep per tick in its own scope; a failed sweep is logged and the next tick tries again).

- `ISessionService.DeleteAsync(id, caller)` deletes at once, for the host or an admin (`RunAsManagerAsync`, so anyone else gets Forbidden), through `ISessionsRepository.DeleteAsync`: the one delete funnel, so every `SessionDeleted` handler runs. `RequestDeletionAsync(id)` is for any guest with access: it schedules `SessionDeletionSettings:DelayDays` (7; a fraction is allowed, so a test can use seconds) from now and is idempotent (success whether or not it was new, first time kept). `ISessionAdminService.CancelDeletionAsync(id)` is admin only (the host has the immediate delete instead) and succeeds when nothing was scheduled.
- In the demo both `DeleteAsync` and `RequestDeletionAsync` answer Forbidden: a demo session ends at its own expiry, and deleting it here would leave its synthetic host profile behind (the sweep of `DemoSessionCleanup` deletes the profile).
- `IScheduledSessionDeletionSweep.SweepAsync` lists the due ids (`ListDueForDeletionAsync`) and deletes each through `ISessionAdminService.DeleteAsync`. A session already gone (the host was quicker) counts as done, one that fails is logged and tried again by the next sweep, and it returns how many it deleted. The interval is `SessionDeletionSettings:SweepIntervalSeconds` (3600).
- Mail: the port is `IMailClient` (`Application/Ports`, `MailMessage(To, Subject, Body)`); the default `NullMailClient` only logs, and the provider's registration replaces it. `MailSettings` (`MailConfiguration`): `BaseUrl`, `ApiKey`, `Sender`, `Recipient`.

### Repository

- `SessionsRepository` takes `IDomainEventDispatcher`. Rename, password, fallback playlist and release load the session tracked, run the action, save and dispatch `DrainEvents()` with `CancellationToken.None`. There is no per-session lock; a session deleted under the save answers false.
- `Session.HostProfileId` is a concurrency token: a save based on a stale host (a claim or release landed between the load and the save) matches no row, and `UpdateAsync` runs the action again on a fresh load, at most 3 attempts, then the `DbUpdateConcurrencyException` propagates (a 500). A release of a session that had no host still raises `HostReleased(null)`, which can drop the player state of a host who claimed right after (accepted).
- Two writes stay plain SQL. `TryClaimAsync` loads the session untracked and lets `Session.ClaimHost(profileId)` decide (`HostClaimOutcome`: `Claimed`, `AlreadyHost` for the host logging in again, `HostedByAnother`; it raises `HostClaimed` only for a claim), then writes with a conditional `ExecuteUpdate` on `HostProfileId IS NULL`, which is what makes the first claim win (the unique index on the host still answers `ProfileHostsAnotherSession`); it dispatches the aggregate's events once that update matched a row. `DeleteAsync` raises `SessionDeleted` itself (reads host and playlist first, like `LobbyGamesRepository.DeleteAsync`).
- **Scheduled deletion.** `Session.DeletionScheduledAt` (nullable UTC, index `IX_Sessions_DeletionScheduledAt`, migration `AddedSessionDeletionSchedule`) is also a concurrency token, so two guests asking at once cannot both schedule: the second save is retried on the fresh row and finds it scheduled (`AlreadyScheduled`, first time kept, one event). `ScheduleDeletionAsync(id, now, delay)` and `CancelDeletionAsync(id)` go through `UpdateAsync` and answer `SessionDeletionScheduleResult` / `SessionDeletionCancelResult` (`SessionNotFound` too). `ListDueForDeletionAsync(now)` reads the ids with `DeletionScheduledAt <= now` from the Reader context, oldest first (the SQL form of `IsDueForDeletion`). The deletion itself still goes only through `DeleteAsync`.
- `SetFallbackSavedPlaylistAsync` goes through `UpdateAsync` like the other fallback actions, so its event is dispatched. `SetFallbackCursorAsync(id, playlistId, expectedCursor, cursor)` and `SetFallbackSavedCursorAsync(id, savedPlaylistId, expectedCursor, cursor)` are bookkeeping and raise nothing. Each is a compare-and-set on the playlist id, the *kind* and the cursor the pick was based on, so a playlist changed or rewound while the filler was reading keeps its new cursor, and an id can never match across kinds.

### Handlers (`Application/Sessions/Handlers`)

- `HostCleanupHandler` (`HostReleased`, `SessionDeleted` → `IHostSessionCleanup`).
- `SlideshowCleanupHandler` (`SessionDeleted`).
- `SessionDeletedPushHandler` (`SessionDeleted`, registered first). The cascade delete took the queue and the games, so clients still connected hear the existing pushes: `RingoChanged` / `ResistanceChanged` (each client fetches again and gets its 404), `ResistanceLobbyChanged`, and an empty `QueueAdvanced` that clears the song on display. The queue list follows with its next poll; a dedicated push is left for later.
- `FallbackPlaylistHandler` (track cache, which it evicts only for Spotify playlists, `FallbackStatusStore`, and `EnsureQueuedAsync` after a change; also on delete).
- `SessionDeletionMailHandler` (`SessionDeletionScheduled`): reads the session and mails the operator through `IMailClient` (`SessionDeletionMail.Compose`: name, code, id and the deletion time, English, no password, hash or token; a line break in the name is turned into a space in the subject). The event is raised only by a new schedule, so one request is one mail. Without `MailSettings:Recipient` it logs a warning that names the session and sends nothing; a session already deleted gets no mail. A failing mail is logged by the dispatcher and the deletion stays scheduled, so the log line is the only trace of a lost mail.
- `SessionLogHandler` (also the two deletion events).
- Because handler failures are only logged, a failed cleanup no longer fails the delete or release request. `SessionAdminService`, `SessionService` and `FallbackPlaylistService` do not clean up themselves.
- Tests: `SessionTests`, `SessionsRepositoryEventsTests`, `SessionHandlersTests`; `FakeSessionsRepository` runs the real actions and dispatches to `Events` when set (`TestEvents.SessionDispatcher`).
