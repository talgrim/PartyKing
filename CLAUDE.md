# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

PartyKing is a party app: guests upload photos that the API serves as a timed slideshow, plus music sessions: each session has its own queue (YouTube links and Spotify tracks, persisted in SQLite) and its own host, who plays it through the Spotify Web Playback SDK. It has a .NET 9 backend (`src/api/PartyKing.sln`) orchestrated by .NET Aspire, and a React + Vite frontend in `src/ui/PartyKing.UI`.
## Commands

Backend (run from `src/api`):
- Build: `dotnet build PartyKing.sln`
- Run everything (API + UI via Aspire): `dotnet run --project PartyKing.AppHost`
- Run the API only: `dotnet run --project PartyKing.API` (the `http` launch profile binds to `http://127.0.0.1:4200`)
- Add an EF migration: `dotnet ef migrations add <Name> --project PartyKing.Persistence --startup-project PartyKing.Persistence --context WriterDbContext`
- Migrations are applied automatically at API startup (`MigrateDb()` in `Program.cs`). The SQLite file is `PartyKing.db` relative to the working directory, or `PARTYKING_DATABASE_PATH` when set.

Frontend (from `src/ui/PartyKing.UI`):
- `npm install`, then `npm start` (Vite dev server on port 2137, host `0.0.0.0`, polling watch for WSL2/Windows HMR)
- `npm run build`
- `npm test` runs `vitest run`. To run a single test: `npx vitest run src/path/to/file.test.ts`. Tests run in jsdom with `testSetup.ts` (jest-dom matchers).

Backend tests (from `src/api`): `dotnet test PartyKing.sln` runs both xunit projects: `PartyKing.Application.Tests` (`SongInputParser`, password hashing, join tokens, queue repository, metered repository decorators, `GameService`, the Never have I ever suggestions and `FallbackChatClient`, with a `FakeChatClient` test double) and `PartyKing.Api.Tests` (action/authorization metrics, metered Spotify client, the 500 problem details response).

## Deployment (Docker / Fly.io)

`Dockerfile` (repo root) builds one image: nginx (`docker/nginx.conf`) serves the UI build and proxies `/api/*` to Kestrel on `127.0.0.1:5000` (prefix stripped); `docker/entrypoint.sh` runs both. `fly.toml` targets `party.talgrim.dev`, one always-on machine (SQLite and in-memory singletons), and the `/data` volume that holds `PartyKing.db` (`PARTYKING_DATABASE_PATH`), Data Protection keys (`DataProtection__KeysDirectory`) and uploaded photos (`ASPNETCORE_WEBROOT`). Secrets (`SpotifySettings__*`, `AdminSettings__*`, `LlmSettings__ApiKey`, `DataProtection__Certificate*`) come from `fly secrets`. The image ships no photos; `GET /sessions/{id}/photos/current` returns 204 when the session has no photos. The UI's `apiUrl` is `/api` in production builds and `http://127.0.0.1:4200` in dev (`VITE_API_URL` overrides). **Uploads are untrusted input**: `PUT /sessions/{id}/photos/{deleteAfterPresentation}` is open to every guest who knows the session password, so `UploadedImageValidator` allows only jpg/jpeg/png/gif/webp, checks the magic bytes, caps a file at 20 MB (100 MB per request via `[RequestSizeLimit]`; Kestrel's default applies elsewhere), and stores the extension and content type of the *detected* format, never the client's. The upload endpoint is rate limited (60/min per IP), static files are served only for those image types with `nosniff`, and nginx adds a sandbox CSP on `/api/Images/` and raises the body limit to 100 MB for `/api/sessions/<guid>/photos/`. The static image files themselves carry no auth (their URLs hold the session GUID and a GUIDv7 file name). The slideshow settings endpoints are `[RequireSessionAccess]` plus the host-or-admin check. CORS exists in Development only (production is same-origin). nginx trusts `Fly-Client-IP`/`X-Forwarded-Proto` only when `TRUST_FLY_CLIENT_IP=1` (set in `fly.toml`); `/health` is served on the internal port 8182, which Fly's check uses, and answers 404 on the public port. The Data Protection keys on `/data/keys` are encrypted with an X.509 certificate (`ProtectKeysWithCertificate`, from the `DataProtection__CertificateBase64` PFX plus optional `DataProtection__CertificatePassword` secrets); the API refuses to start when `DataProtection__KeysDirectory` is set without the certificate. Keys written before encryption stay readable. See the README section "Wdrożenie".

## Architecture

Project dependencies (layered, top → bottom):
- **AppHost**: Aspire host. Starts `PartyKing.API` and the UI as an npm app on port 2137.
- **API**: controllers plus `Program.cs`. CORS allows any origin with credentials. Static files from the web root serve the images (`Images/Uploaded/{sessionId}`, created at startup and not in git).
- **Application**: services (`SlideshowService`, `QueueService`, `SessionService`, `AdminService`, `SpotifyService`, `HostTokenProvider`), options binding (`SlideshowConfiguration` ← `SlideshowSettings`, `AdminConfiguration` ← `AdminSettings`), and DTO mappings. References Contract and Infrastructure.
- **Contract**: public DTOs under `V1/`, returned by controllers.
- **Infrastructure**: repositories that wrap EF Core. References Persistence and Domain.
- **Persistence**: EF Core SQLite `DbContext`s, entity configurations, migrations, seed data.
- **Domain**: entities (`SlideshowImage`, `SlideshowSettings`, `QueueItem`, `SpotifyProfile`, `Session`, `AdminAccount`, `OAuthState`), enums, read/write models.
- **ServiceDefaults**: Aspire OpenTelemetry/health/resilience defaults (`AddServiceDefaults`, `MapDefaultEndpoints`).

Each layer registers its own services through a `DependencyInjection.cs` extension (`RegisterApplication`, `RegisterInfrastructure`), and `PartyKing.API/DependencyInjection.cs` chains them.

Key patterns and gotchas:
- **Reader/Writer DbContexts**: `ReaderDbContext` and `WriterDbContext` both derive from `PartyKingDbContextBase`, which hardcodes `UseSqlite("Data Source=PartyKing.db")` in `OnConfiguring`. They're registered with `AddDbContextFactory`. Repositories are **singletons** and create short-lived contexts through the factories. Migrations target `WriterDbContext`, and the snapshot file is `WriterDbContextModelSnapshot.cs`.
- **Stateful singletons**: `SlideshowService` and `SlideshowImagesRepository` are singletons that hold in-memory state: `SlideshowService` keeps, per session id, the current image and its expiration time (with a per-session lock); the repository keeps only the web root path. `Program.cs` awaits `ISlideshowService.InitializeAsync` once at startup, after the migration and admin seed: it creates the `Images/Uploaded` folder under `WebRootPath` and removes the old shared `SampleImages` folder (the migration `MadeSlideshowPerSession` deleted its rows).
- **Slideshow flow**: per session. `GET /sessions/{id}/photos/current` (`[RequireSessionAccess]`) returns the session's current image, or 204 when there is none (there are no placeholders). While a host or admin displays the slideshow (see Slideshow push) a server timer advances it at `SlideTime`; without one the first read after the expiration advances it, so a client without a live connection still sees it move. When an image with `DeleteAfterPresentation` is rotated out, it gets deleted. Uploads go to `Images/Uploaded/{sessionId}/`; `SessionService.DeleteAsync` removes that folder and the in-memory slide (`ISlideshowService.DeleteSessionAsync`), the rows go with the cascade delete.
- **Settings live in the DB**: one `SlideshowSettings` row per session (`SessionId` is the key, cascade delete), edited by the host or an admin through `GET`/`PUT sessions/{id}/slideshow-settings` (`[RequireSessionAccess]` plus `ISessionService.AuthorizeManagerAsync`, 403 for anyone else) and shown as a form (`SlideshowSettingsForm`) in the session settings dialog. A session without a row uses the defaults (`SlideshowSettings:SlideTime` from appsettings, `AutoRepeat` on, `StartFromBeginning` on); the slide time must be 1 s to 1 h. The upload directory still comes from appsettings.
- **Slideshow push**: `SessionHub` has two methods, `WatchSlideshow` (host or admin only, `HubException` otherwise) and `StopWatchingSlideshow`, which `SlideshowView` calls through the hub connection while it is mounted (a collapsed drawer unmounts it, so it doesn't count). `SlideshowWatchers` (singleton) counts the watching connections per session, and `OnDisconnectedAsync` removes a closed one. The first watcher catches up an expired slide once and arms the session's timer (`SlideshowScheduler`, one `Task.Delay` per session, the same shape as `PlayerConnectionWatchdog`); the timer rotates under the per-session lock, re-arms, and pushes the payload-free `SlideChanged` to the whole session group only when the image on display changed (clients then `GET` the current slide, so no image URL goes out in a push). The last watcher leaving cancels the timer, so nothing rotates or deletes `DeleteAfterPresentation` images while nobody watches. A `SlideTime` change restarts the slide on display with the new time counted from now, and an upload into an empty slideshow rotates at once. `useSlideshowWatch` re-sends `WatchSlideshow` after every reconnect (the server forgets it with the old connection); the UI polls the slide every 60 s while the hub is connected and every 5 s otherwise.
- **Metrics**: the meters `PartyKing.API` (`ActionMetricsFilter` times every controller action, `AuthorizationMetrics` times cookie auth and session access), `PartyKing.Infrastructure` (`Metered*Repository` decorators registered through `AddMetered`, plus the queue advance lock wait) and `PartyKing.Infrastructure.Spotify` (`MeteredSpotifyIntegrationClient`) record durations in milliseconds. `ServiceDefaults` exports them through OpenTelemetry and a Prometheus endpoint at `/metrics`; nginx exposes it only on the internal port 8183, which Fly scrapes (`[metrics]` in `fly.toml`). Unhandled exceptions answer a 500 ProblemDetails.
- **Errors**: `CoreController` maps `ErrorOr` errors to ProblemDetails (Validation→400, Unauthorized→401, NotFound→404, Conflict→409).
- **Sessions**: a `Session` (GUID id, unique short `Code` from `SessionCodeGenerator`, name defaulting to "New session", nullable `HostProfileId`) owns one `QueueItem` queue (`QueueItem.SessionId`, cascade delete). Only an admin creates, deletes or releases sessions (`/admin/sessions...`); the host or an admin renames a session and changes its password (see Session password). `GET /sessions` and `GET /sessions/{id}` are public. Each session has its own slideshow (see Slideshow flow).
- **Session password**: every session has a mandatory password (`Session.PasswordHash`, PBKDF2 through `IPasswordHasher`, 4-100 characters, set by `POST /admin/sessions`, changed by the host or an admin through `PUT /sessions/{id}/password`). Everyone who joins, admins included, must unlock the session with `POST /sessions/{id}/join` (rate limited, 10 per minute per IP; 401 for a wrong password and for an unknown session alike, and it verifies against a dummy hash so timing doesn't tell them apart). `SessionService.JoinAsync` returns an access stamp (hash of the password hash), which `ICookieAuthorizationHandler.GrantSessionAccess` stores in the signed `cookie.partyKing.sessions` cookie together with the session id (at most 20 sessions). `[RequireSessionAccess]` (`SessionAccessFilter`) checks it against the route's `sessionId` and answers 401 on every public session endpoint (`GET /sessions/{id}`, `/me`, `now-playing`, `songs` (list, add, remove), `songs/next`, `tracks`, `host-login-urls`, `player/state`) and on the admin player endpoints (`admin/sessions/{id}/player/commands` and `songs/next`). Changing the password changes the stamp, so old unlocks stop working; `ChangePasswordAsync` returns the new stamp and the controller grants it to the caller again, so the host or admin who changed it stays unlocked. **Join with QR code**: the host and admins (`useViewerRole`) get a "Show QR code" button (`JoinQrCode`, MUI `Dialog`) on the session page. `POST /sessions/{id}/join-token` (`[RequireSessionAccess]`, 403 unless host or admin) returns a stateless token (`JoinTokenProtector`, Data Protection, holds session id, access stamp and a 5-minute expiry; no DB table), and the dialog shows a QR of `/s/{id}?join=<token>`, replaced 30 s before it expires. `MusicQueue` redeems `?join=` through `POST /sessions/{id}/join-with-token` (same `session-join` rate limit, plain 401 on any failure), which grants the same session cookie as `/join`, then strips the param. A token is reusable until it expires and can't be revoked individually, but changing the password changes the stamp and kills all of them. Delete and release host are admin-only and need no session password; rename (`PATCH /sessions/{id}`) and change password are host-or-admin (`RenameAsync`/`ChangePasswordAsync` take `profileId` and `isAdmin` and answer Forbidden otherwise) and, being `[RequireSessionAccess]`, need the session unlocked, so an admin who doesn't know the password can't reset it (accepted). `GET /sessions` stays public (id, code, name, host). The UI shows `SessionPasswordForm` on `/s/:sessionId` when `getSession` answers 401; the axios instance sends credentials on every call.
- **Music queue**: `QueueItem`s (YouTube or Spotify) live in the `QueueItems` table, managed by the singleton `QueueRepository`, which has no in-memory queue state except a per-session advance lock. Everything is scoped by session: guests add songs without logging in via `POST /sessions/{id}/songs` (body `{input}`: a Spotify track URL/URI or a YouTube URL, parsed by `SongInputParser`) and search Spotify with `GET /sessions/{id}/tracks?query=`. For YouTube links `SongInputParser` extracts the video id (playlists, channels and searches are rejected), and `QueueService` looks the video up through the keyless oEmbed endpoint (`IYoutubeOEmbedClient` in `PartyKing.Infrastructure.Youtube`): the title, author and thumbnail fill the `QueueItem`, a video whose owner disabled embedding is rejected with a 400, and when YouTube can't be reached the link is queued with the URL as its title. `GET /sessions/{id}/songs` lists the queued items only: the song being played (status `Playing`) is not among them, it comes from `GET /sessions/{id}/now-playing`. `POST /sessions/{id}/songs/next?currentSongId=` is host-only: `[AuthorizeByCookie]` plus a check that the cookie's profile id is the session's `HostProfileId` (403 otherwise). `currentSongId` is the song the player thinks is playing (none when omitted); `QueueRepository.AdvanceAsync` advances only when that is really the `Playing` item, otherwise it advances nothing and returns the song that is playing. That keeps the host's end-of-song call from skipping a song an admin already skipped. `DELETE /sessions/{id}/songs/{songId}` removes a song that is still `Queued`: it has no auth attribute, the controller reads the host cookie and the admin cookie (like `GET /me`) and `QueueService.RemoveAsync` answers 403 unless the caller is an admin or the session's host (404 for an unknown session or song, 409 when the song is already playing or played). `QueueRepository.RemoveAsync` hard-deletes the row under the same per-session lock as `AdvanceAsync` and only matches songs of that session. `GET /spotify/token` needs a host login but is per browser, not per session.
- **Fallback playlist**: the host (or an admin) can set a Spotify playlist the host owns that plays whenever the queue is empty. `Session` holds `FallbackPlaylistId`/`FallbackPlaylistName`/`FallbackShuffle`/`FallbackCursor`; `QueueItem.IsFallback` marks the songs the server queued from it (the UI shows a "from playlist" badge). `PUT /sessions/{id}/fallback-playlist` (`FallbackPlaylistController`, `[RequireSessionAccess]`, host or admin through `AuthorizeManagerAsync`) takes `{playlist, shuffle}` (link or `spotify:playlist:` URI, parsed by `PlaylistInputParser`; empty clears it); `FallbackPlaylistService` checks with the *session host's* token that the playlist's owner is the host (400 otherwise, 409 when the session has no host). `GET /sessions/{id}/host-playlists` (host only) lists the playlists the host owns for the picker in `FallbackPlaylistForm` (needs the `playlist-read-private` scope, so hosts who logged in earlier get 409 "log in again"). **Refill**: `IFallbackQueueFiller.EnsureQueuedAsync` keeps one `Queued` fallback song in the queue whenever it has none, so guests' songs land behind it and the playlist continues after them. It runs before and after every advance (`QueueService.AdvanceAndNotifyAsync`, `PlayerService.SkipAsync`), after a removal and after the playlist is saved. It adds through `IQueueRepository.AddIfNoneQueuedAsync` (same per-session lock as advance/remove, so a guest's concurrent add wins). Tracks come from `GetPlaylistTracksAsync` (episodes and local files skipped), cached 5 minutes (`PlaylistTrackCache`); in order it uses `FallbackCursor` (wraps around), shuffled it picks randomly but not the playing song. A failure (no host, dead Spotify login, empty or unreadable playlist) never throws: `FallbackStatusStore` keeps the message per session in memory and `POST player/state` returns it as `fallbackError`, which `HostPlayer` shows. Releasing the host clears the fallback fields (the playlist belongs to the host who chose it). To change only the shuffle flag, save the playlist again.
- **Player state and remote control**: the music plays in the host's browser tab (`HostPlayer`), so the server only knows what that tab reports. `PlayerStateStore` (in-memory singleton, behind `IPlayerStateStore`) keeps per session what the host's player last reported (song id, paused, time); the player counts as connected when it reported within 30 s (`PlayerStateStore.ConnectionTimeout`). The host's player calls `POST /sessions/{id}/player/state` ({songId, paused}, host-only) every ~10 s as a keepalive and at once on every change; `PlayerStateStore.Report` says whether the report changed anything, and `PlayerStateChanged` is broadcast only then. The response carries the one pending admin command (`Pause`/`Resume`) and `fallbackError`, but both are also pushed over SignalR (`PlayerCommand` from `PlayerService.SendCommandAsync`, `FallbackErrorChanged` from `FallbackStatusStore` when the message changes; the hub is role-agnostic, so they go to the whole session group and only `HostPlayer` acts on them, through the `pushHandlers` ref that `MusicQueue` passes to `useSessionMusicHub`). The pending command stays in the store until the next report, so a push missed during a reconnect is still delivered (applying it is idempotent), and the player reports right after a SignalR reconnect. `GET /sessions/{id}/now-playing` (public, `PlayerService`) returns the playing song (title, artists, album art or thumbnail), `paused` (only if reported for that very song) and `playerConnected`. An admin who is not the host has no host cookie, so `POST /admin/sessions/{id}/player/commands` queues a pause/resume command and `POST /admin/sessions/{id}/songs/next` advances the queue; both answer 409 when no player is connected, and the host's player picks a skipped-to song up by following `now-playing`. `GET /sessions/{id}/me` (public, accepts either cookie) returns `{isHost, isAdmin}` so the UI knows whether to show controls.
- **Lyrics**: everyone who unlocked the session gets the drawer and the maximized view with line-synced lyrics; the host and admins can also switch them to the slideshow (guests have no slideshow, so they never request photos, and `SlideshowControls` `lyricsOnly` hides the switch). `GET /sessions/{id}/now-playing/lyrics` (`LyricsController`, `[RequireSessionAccess]` only; 404 when nothing plays or no synced lyrics match) returns `{songId, lines:[{timeMs,text}]}` for the playing song. `LyricsService` asks LRCLIB (`PartyKing.Infrastructure.Lyrics`, `ILrclibClient`, keyless; returns an `Unavailable` result instead of throwing; not metered) first by track+artist, then by free text; `LyricsQuery` derives title/artist (Spotify: strip remaster/feat suffixes; YouTube: best-effort cleaning and splitting of "Artist - Title"), `LyricsMatcher` takes a synced, non-instrumental candidate whose title matches and whose duration is within 5 s (when known). `LyricsCache` (singleton) remembers found lyrics 24 h and misses 1 h per song URL; an unreachable LRCLIB is not cached. **Position sync**: `POST player/state` also carries `positionMs` and `seeked`; `PlayerStateStore` extrapolates the position in `Get` (stored position plus the time since the last report unless paused), and only a song/pause change or a seek counts as a change, so position adds no broadcasts or polling (`now-playing` and `PlayerStateChanged` carry `positionMs`; the existing 4 s poll re-anchors). The host's player detects seeks (Spotify: `player_state_changed` position vs `createPositionTracker`; YouTube: `onSeeked`). UI: `useLyrics` (SWR per song), `LyricsView` (250 ms local tick from the anchored position, `lyricsTiming.ts`, timing offset ± stored in `localStorage`), and a lyrics toggle in `SlideshowControls` that stays enabled and shows a crossed-out icon when the song has no lyrics (mode persisted as `partyking.showLyrics`).
- **Games**: a games page per session at `/s/:sessionId/games` (`Games`), reached only from the "Games" link on each session row of the admin panel for now. `GET /sessions/{id}/games` (`GamesController`, `[RequireSessionAccess]`, host or admin through `AuthorizeManagerAsync`, 403 for guests, which the UI answers by redirecting to the session page) returns a static list from `GameService` (`ringo`, `never-have-i-ever`; no DB table). `GET /sessions/{id}/games/never-have-i-ever/suggestions` (same auth, rate limit `game-suggestions`, 10 per minute per IP) returns `{suggestions, fromFallback}`: `NeverHaveIEverSuggestionService` asks an LLM for 5 spicy statements in Polish (JSON array, parsed by `Parse`: blanks, duplicates and statements over 200 characters dropped) and falls back to a built-in Polish list when there is no API key, the call fails or the answer can't be parsed (`fromFallback`, the UI shows a notice). `NeverHaveIEverSuggestions` shows the button and the 429 message.
- **LLM**: `PartyKing.Infrastructure.Llm` registers an `IChatClient` (Microsoft.Extensions.AI) on the OpenAI SDK pointed at Gemini's OpenAI-compatible endpoint (free tier). `LlmSettings`: `ApiKey` (secret; locally in the untracked `appsettings.Local.json`, on Fly `LlmSettings__ApiKey`), `Model`, optional `FallbackModel`, `ReasoningEffort` (`low`/`medium`/`high`, Gemini rejects `minimal`; default `low`) and `BaseUrl`. The SDK's own retries are off (`maxRetries: 0`) and the network timeout is 30 s. `ProviderErrorChatClient` turns an SDK `ClientResultException` into `LlmProviderException` (`IsTransient` for 429 and 5xx); when `FallbackModel` is set, `FallbackChatClient` retries on it only after a transient error or a timeout (no `ReasoningEffort` there), not after 400/401/404 or the caller's cancellation. Microsoft.Extensions.* packages are on 9.0.10 across the projects because Microsoft.Extensions.AI 9.10.2 needs it.
- **Session host**: one host per session, and one Spotify account can host one session (unique index on `Session.HostProfileId`). The host flow: `POST /sessions/{id}/host-login-urls` stores a short-lived `OAuthState` (the OAuth `state` parameter, single use) and returns the Spotify URL; Spotify redirects to the fixed `/callback`, which posts `{code, state}` to `POST /authenticate`; `SessionsRepository.TryClaimAsync` then atomically claims the session (first account wins, others get 409, the current host logging in again is fine). An admin can release the host (`DELETE /admin/sessions/{id}/host`). `HostTokenProvider` (singleton) caches and refreshes one access token per host profile, resolved through the session, and returns `Error.Unauthorized` when the refresh token is dead (the host logs in again). Spotify profile ids are strings, and `SpotifyProfile.DisplayName` is shown as "Current Host". The OAuth redirect URI uses `127.0.0.1`, so log in via `http://127.0.0.1:2137/...`, not `localhost` (the Vite dev server redirects `localhost` to `127.0.0.1`, and the Aspire dashboard link uses `127.0.0.1`, because the SameSite=Lax login cookies don't reach the API from a page opened via `localhost`). Known dev limitation: YouTube refuses to play embeds (player error 150) when the page's origin is an IP address such as `127.0.0.1`, while it works from `localhost`. the host's browser reads `GET https://api.spotify.com/v1/me/player` (scope `user-read-playback-state`, so hosts who logged in before it was added get a 403 and just see the normal button until they log in again). While the host has not started the player and the session's playing song is a Spotify track that this account has on another device (playing or paused), `HostPlayer` shows "Play here" instead of "Start the music" (`takeover.ts`), and `SpotifyPlayer` continues the song with `position_ms` in its `/me/player/play` call, so it starts at the other device's position and as a single-track context. Spotify login needs `127.0.0.1`, so YouTube songs can't play in local dev; it goes away when the app is deployed on a real domain.
- **Cookies**: `cookie.partyKing.user` (the host's profile id) and `cookie.partyKing.admin` (the admin account id) are signed with ASP.NET Data Protection in `CookieAuthorizationHandler`, so clients can't forge identities; `cookie.partyKing.auth` holds the host's Spotify access token. The `CustomCookie` scheme adds `NameIdentifier` (profile id) and `Authentication` (access token) claims; the `AdminCookie` scheme backs `[AuthorizeAdmin]`.
- **Admin accounts**: stored in `AdminAccounts` with PBKDF2 password hashes. When none exists, the first one is created at startup from `AdminSettings:Username` plus either `Password` (plain text, hashed on seeding) or `PasswordHash` (put them in the untracked `appsettings.Local.json`). Generate a hash with `dotnet run --project PartyKing.API -- hash-password` (run from `src/api`; it prompts for the password and prints the value, without starting the app). `POST /admin/login` is rate limited (10 per minute per IP).
- `PartyKing.Infrastructure.Spotify` wraps the Spotify Web API client (`ISpotifyIntegrationClient`: auth, search, track lookup). `PartyKing.Infrastructure.Youtube` wraps YouTube's oEmbed endpoint (`IYoutubeOEmbedClient`).

Frontend (`PartyKing.UI/src`):
- React 19, react-router (`router/routes.tsx`: `/` Home lists sessions with a code search, `/s/:sessionId` MusicQueue, the one page of a session: everyone sees `NowPlayingCard` (art, title, artist, paused badge) and the queue; the viewer's role from `useViewerRole` (`GET /sessions/{id}/me`) adds, for the host and any admin, a red delete icon on each "Up next" row (`Queue` prop `canRemove`, deletes at once, no confirmation), and the host's `HostPlayer` (plays the music, so the host must keep the page open; `VolumeControl` sets the volume, stored in `localStorage` through `usePersistedNumber`; a YouTube player error skips to the next song, but only until 2 videos fail in a row; then it stops and shows a message until the host presses "Next song" or a song plays; `ErrorLog` lists errors for the admin only) or, for an admin who is not the host, `AdminPlayerControls` (Play/Pause and Next through the admin endpoints, disabled while no player is connected). A host whose login expired uses "I'm the host" in `SessionHeader` to log in again; `SessionHeader` also shows a gear (`SessionSettings`, MUI `Dialog` with `SessionNameForm`, `SessionPasswordChangeForm` and `SlideshowSettingsForm`) to the host and admins, `/callback` Spotify redirect, `/admin` admin login and session panel (create, copy link, release host, delete; rename, password and slideshow settings live on the session page), and photo upload as a dialog on the session page (the "Upload photos" button in `PageNavigation`, `PhotoUploadDialog` with `PhotoUploader`; full screen below 640 px, can't be closed while an upload runs; its open state is the `?upload=1` query parameter, `useUploadDialog`, so Back closes it and a reload reopens it; a 401 during the upload closes it and the page asks for the password again; the old `/s/:sessionId/upload` route redirects there through `UploadRedirect`; Home has no slideshow links). There is no separate slideshow route: the host and admins (`useViewerRole`) get `SlideshowView` on the session page, in a left drawer that is open by default (closed by default on a touch device, `isMobileDevice`) and hidden with a toggle (persisted in `localStorage` through `usePersistedFlag`), and a "Maximize" button opens `MaximizedView`, a `fixed inset-0` overlay with the slideshow, `NowPlayingOverlay` (title and artist only) and a read-only `QueueList` that sits on the right on a landscape or wide screen (a phone turned sideways included) and below the slideshow on a portrait one, and that a queue button next to the X hides (kept in `localStorage` as `partyking.maximizedQueueOpen`; Esc or the X exits). The overlay covers the page without unmounting it, so the host's `HostPlayer` keeps playing. `SlideshowView` fills its parent's box, and guests never request the photos from this page), MUI + Tailwind v4, axios + SWR.
- The API base URL comes from `src/envVariables.ts`: `VITE_API_URL` if set, else `http://127.0.0.1:4200` in dev (must match the API launch profile) and `/api` in production builds. To test from phones on the LAN, change both `envVariables.ts` (or set `VITE_API_URL`) and `src/api/PartyKing.API/Properties/launchSettings.json` to the machine's LAN IP, but don't commit that change. UI polling (SWR `refreshInterval`): slide 60 s with the hub connected and 5 s without (SlideChanged is pushed), queue 5 s, now-playing 4 s, session 30 s, session lists 10 s; the host player reports state every 10 s (and on every change) with an 8 s timeout. Axios is configured in `src/service/request.ts`, and the `@/` import alias maps to `src/`.

## CI
`.github/workflows/ci.yml` (PRs) runs `dotnet test PartyKing.sln` (all backend tests), `npm test` (all frontend tests) and `npm run build`. `deploy.yml` runs `flyctl deploy --remote-only` on push to `master`. `/health`, `/alive` and `/metrics` are mapped in every environment (`MapDefaultEndpoints`); nginx keeps them off the public port.

## Conventions
- Commits follow the Conventional Commits format.
- Use subagent Explore for codebase exploration.
- Don't commit changes until explicitly stated.
- Stick to SOLID.
- Commit tests in a separate commit.
- Commits should be atomic.
- When exploring automatically assume that the user is in "Interview" mode, meaning that you can ask him questions regarding the task. Also don't make any changes when prompt ask only for exploring and analysis.
